# 내 방식 QR — 공통 SDK v0.5.5 최종 안정화: 마지막 버튼 접근성 25건 분석 및 릴리스

현재 데모커피 프로젝트에서 공통 접근성 SDK `@naebangsik/kiosk-accessibility-sdk@0.5.4`를 개발하고 있습니다.

직전 작업에서 무인민원발급기에서 발견된 **1440×900 넓은 화면의 상단 제목 잘림 문제**를 일반 HTML fixture로 재현했습니다.

원인은 제한된 하단 viewport 안에서 큰 min-height 콘텐츠가 `justify-content: center`로 배치되면서 첫 제목이 스크롤 영역 위쪽으로 밀리는 현상이었습니다.

공통 SDK의 `packages/kiosk-accessibility-sdk/src/bottom-viewport.ts`를 수정해 등록된 스크롤 영역의 세로 중앙 정렬을 안전하게 처리하도록 했습니다.

핵심 재현 사례에서는 문제가 해결됐습니다.

- 하단 viewport 시작 y=166px
- 수정 전 제목 시작 약 y=143px
- 수정 후 제목 시작 약 y=202px
- 제목 전체 표시 및 hit-test 정상
- 1440×900 핵심 사례에서 마지막 버튼 표시·클릭 성공
- 독립 fixture 103개 조합에서 상단 제목 잘림 0건

하지만 전체 fixture 103개 조합 중 **마지막 버튼 표시·클릭 검사가 25개 조합에서 통과하지 못했습니다.**

따라서 SDK v0.5.5는 아직 제작하지 않았고, package.json 버전도 0.5.4로 유지한 상태입니다.

이번 작업은 남아 있는 실패 원인을 분석하고, 필요한 경우 범용 SDK를 보완한 뒤, 모든 필수 회귀 검증을 완료하여 v0.5.5를 정식 패키징하는 것입니다.

**실패한 검사를 삭제하거나 합격 조건을 완화해 릴리스하지 마세요.**

## 1. 기존 작업 상태 보존

먼저 현재 코드를 확인해 주세요.

- v0.5.4 공개 API와 소스 상태
- `bottom-viewport.ts`의 안전한 중앙 정렬 수정
- 기존 103개 브라우저 조합 fixture
- 실패한 25개 조합
- SDK 버전 및 tarball 아카이브
- 기존 화면 전환 API `notifyScreenChange()`

이미 검증된 수정은 보존합니다.

문제 해결을 위해 SDK 구조 전체를 다시 설계하지 마세요.

## 2. 실패한 25개 조합 전수 분석

먼저 실패한 모든 조합을 정확하게 분류합니다.

각 실패에 대해 다음을 기록해 주세요.

- 테스트 ID
- 화면 크기
- DOM 구조
- 기본·큰 글씨 프로필
- viewportMode 비율
- QR 도크 유무
- 고정 하단 조작부 유무
- 스크롤 소유자
- 마지막 버튼의 실제 DOM 좌표
- 마지막 버튼의 화면상 좌표
- 스크롤 영역의 scrollHeight / clientHeight
- 최대 scrollTop
- 실제 scrollTop
- hit-test 대상
- 클릭 이벤트 발생 여부
- 실패한 정확한 assertion

결과를 표로 정리하고 실패 유형별로 묶어 주세요.

**단순히 25건 실패라는 숫자만 보고하지 말고, 각각 왜 실패했는지 설명할 수 있어야 합니다.**

## 3. 실패 유형 구분

다음 가능성을 구분해서 조사합니다.

### A. 실제 콘텐츠 접근 불가

- 마지막 버튼이 스크롤 끝에서도 보이지 않음
- 버튼이 clipping 영역 밖에 위치
- 스크롤 범위가 부족함
- 고정 QR 도크 또는 업무 버튼 아래에 가려짐

이 경우는 실제 접근성 문제이므로 수정이 필요합니다.

### B. 정렬과 스크롤 범위의 충돌

- 안전한 중앙 정렬 적용 후 콘텐츠 시작은 정상
- 반대로 마지막 콘텐츠의 스크롤 범위가 줄어듦
- flex/grid의 min-height 또는 overflow가 영향을 줌
- 정렬 스타일 복원이 누락됨

이 경우 SDK 수정이 새로운 문제를 만들었는지 확인합니다.

### C. 테스트 조작 방식의 문제

- scrollTop을 최대값으로 이동했지만 레이아웃이 아직 안정되지 않음
- 실제 버튼 좌표 대신 이전 프레임의 좌표로 클릭
- 테스트가 잘못된 스크롤 소유자에 스크롤 입력
- 클릭 좌표가 다른 요소를 가리킴
- 버튼은 접근 가능하지만 테스트가 이를 감지하지 못함

이 경우 테스트 구현을 수정할 수 있습니다.

다만 **실제 브라우저에서 버튼이 보이고 클릭 가능하다는 증거가 있어야만 테스트 문제로 판정**합니다.

### D. 경계 위치 문제

- 스크롤을 절대 최댓값으로 이동했을 때 버튼이 일부 가려짐
- 약간 위로 이동하면 클릭 가능
- 일반 휠·터치 제스처에서는 접근 가능

이 경우에도 실패를 무조건 무시하지 마세요.

스크롤 마지막 위치에서 버튼이 가려지는 이유와 실제 사용자에게 미치는 영향을 판단하고, SDK 계약상 마지막 콘텐츠가 완전히 접근 가능해야 하는지 확인해 주세요.

사용자가 별도의 정밀한 스크롤 조정 없이 마지막 버튼을 볼 수 있는 것이 목표입니다.

## 4. 핵심 1440×900 상단 잘림 수정 유지

다음 조건은 반드시 유지합니다.

- 큰 글씨·큰 버튼·고대비
- 하단 viewport 80%
- min-height 약 780px
- 세로 중앙 정렬
- viewport 시작 y=166px 부근
- 첫 제목 전체 표시
- 첫 제목 hit-test 정상
- 마지막 버튼까지 스크롤 가능

수정 과정에서 `justify-content` 안전 정렬이 해제되거나 이전 상단 잘림 문제가 재발해서는 안 됩니다.

SDK는 특정 키오스크의 CSS 클래스나 특정 픽셀 높이를 하드코딩하지 않아야 합니다.

## 5. 공통 SDK 수정 원칙

실제 SDK 결함이 확인된 경우에만 SDK를 수정합니다.

우선 다음 영역을 조사해 주세요.

- `bottom-viewport.ts`
- scrollArea 등록 및 실제 스크롤 소유자
- 안전한 중앙 정렬 처리
- flex/grid 컨테이너의 overflow
- min-height 처리
- 하단 viewport 높이 계산
- QR 도크 크기 변화
- 고정 하단 조작부 회피
- scroll-padding 또는 콘텐츠 끝 여유 공간
- SDK 스타일 복원

목표:

- 상단 콘텐츠 접근 가능
- 마지막 콘텐츠 접근 가능
- 글씨·버튼 크기 유지
- 전체 화면 축소 없음
- 이중 스크롤 없음
- QR 도크·고정 버튼과 겹침 없음
- 기존 호스트 CSS를 무차별적으로 덮어쓰지 않음

기존 어댑터만으로 해결 가능하다면 공개 API를 불필요하게 추가하지 마세요.

## 6. 브라우저에서 실제 사용자 조작 검증

마지막 버튼은 단순 DOM 존재 여부가 아니라 실제 클릭까지 확인합니다.

각 문제 조합에서 다음 순서로 시험해 주세요.

1. 화면 상단 진입
2. 첫 제목 전체 표시 확인
3. 실제 휠 또는 터치 스와이프로 아래로 이동
4. 마지막 버튼이 화면에 들어오는지 확인
5. `elementFromPoint()`로 클릭 대상 확인
6. 실제 마우스 또는 터치 클릭
7. 버튼의 동작 이벤트 발생 확인
8. 다시 위로 스크롤해 제목 표시 확인

자동 `scrollIntoView()`만 실행하고 클릭 가능하다고 판단하지 마세요.

필요하면 스크롤 소유 요소에 실제 입력을 전달해 검증합니다.

클릭 대상이 QR 도크나 고정 조작부라면 실패로 판정합니다.

## 7. 독립 fixture 전체 재검증

기존 103개 조합을 모두 다시 실행합니다.

검증 사항:

- 상단 제목 잘림 0건
- 마지막 버튼 접근·클릭 성공
- QR 도크와 고정 조작부 충돌 없음
- 화면 가로 넘침 없음
- 실제 활성 스크롤 소유자 판정
- 이중 스크롤 없음
- 하단 60·70·80% 계산 정상
- 확대 프로필에서도 폰트·버튼 축소 없음
- 안전 정렬 해제 시 기존 호스트 스타일 복원

검증 화면 크기:

- 320×844
- 360×667
- 390×844
- 1080×1920
- 1440×900
- 1920×1080

기존 실패 조합을 제외하거나 조건을 변경해 분모를 줄이지 마세요.

## 8. 화면 전환 API 전체 회귀

SDK v0.5.4의 `notifyScreenChange()` 기능을 반드시 검증합니다.

다음 시나리오를 실제 Chromium에서 시험해 주세요.

- 문서 스크롤 → 내부 스크롤 화면
- 내부 스크롤 → 문서 스크롤 화면
- QR 도크 첫 화면 → 일반 업무 화면
- 일반 업무 화면 → QR 도크 첫 화면
- 하단 60·70·80% 유지하며 화면 전환
- 화면 변경 후 첫 제목 표시
- 같은 screenId 재통지 시 스크롤 유지
- 모달 열기·닫기 시 스크롤 유지
- 사용자가 직접 스크롤한 뒤 늦은 SDK 초기화가 재실행되지 않음
- `endSession()` 후 일반 화면 및 초기 스크롤 복원

화면 전환 시 실제 첫 콘텐츠가 보이는지 확인하고, scrollTop=0만으로 합격 처리하지 마세요.

## 9. QR 도크·스크롤 안내·스마트 길잡이 회귀

다음을 확인해 주세요.

- 첫 화면 QR 도크 정상 표시
- QR 도크가 큰 글씨에 따라 커지면 실제 높이 재측정
- 업무 화면 진입 시 도크 제거
- 첫 화면 복귀 시 도크 재표시
- QR 도크 중복 생성 없음
- `no-safe-space` 문제 재발 없음
- 스크롤 안내는 최하단에서 숨김
- 위로 돌아오면 재표시
- 안내가 고정 필수 버튼을 가리지 않음
- 스마트 길잡이 표시 시 일반 스크롤 안내 숨김
- 모달 종료 후 스크롤 위치 유지

안내를 표시하기 위해 콘텐츠 높이를 불필요하게 줄이거나 새로운 이중 스크롤을 만들지 마세요.
