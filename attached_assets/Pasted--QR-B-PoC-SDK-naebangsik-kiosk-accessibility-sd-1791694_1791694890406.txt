# 내 방식 QR — 하단 조작 모드 방법 B 기술 검증 (PoC)

현재 데모커피 프로젝트에는 공통 접근성 SDK `@naebangsik/kiosk-accessibility-sdk@0.3.6`이 적용되어 있습니다.

이번 작업에서는 휠체어 이용자 등 화면 상단까지 손을 뻗기 어려운 사용자를 위해, 키오스크 화면을 아래쪽으로 재배치하는 하단 조작 모드를 기술 검증하려고 합니다.

**중요: 이번에는 정식 기능을 개발하는 것이 아니라 방법 B의 구현 가능성을 확인하는 PoC입니다.**

방법 B는 전체 화면을 `transform: scale()`로 축소하는 것이 아닙니다.

기존 글씨와 버튼의 실제 표시 크기를 유지하면서, 키오스크의 주요 화면을 아래쪽 60~80% 영역에 배치하는 방식입니다.

방법 B가 구조적으로 어렵거나 기존 기능을 심각하게 손상시키면 무리하게 구현하지 말고, 방법 A(화면 전체 비례 축소)의 필요성을 판단할 수 있도록 결과를 보고해 주세요.

---

## 1. 이번 실험의 목표

방법 B에서 다음 다섯 가지를 검증합니다.

1. 화면의 주요 UI를 아래쪽 70% 영역으로 이동할 수 있는가?
2. 이동 후에도 글씨와 버튼의 실제 픽셀 크기를 유지할 수 있는가?
3. 줄어든 표시 영역 안에서 전체 콘텐츠를 스크롤할 수 있는가?
4. 버튼과 메뉴의 시각적 위치와 실제 터치 영역이 일치하는가?
5. 기존 큰 글씨·큰 버튼·고대비 설정과 동시에 사용할 수 있는가?

가능하면 60%, 70%, 80%도 시험하되, 가장 먼저 70%가 안전하게 작동하는지 검증해 주세요.

## 2. 기존 구조 먼저 분석

코드 수정 전에 다음을 확인하고 간략하게 정리해 주세요.

- 데모커피의 화면 최상위 컨테이너
- 문서 전체 스크롤과 내부 스크롤 구조
- position: fixed / sticky 사용 요소
- vh, dvh, min-height: 100vh 사용 요소
- 카테고리 가로 이동 목록
- 하단 주문 확인·결제 버튼
- 모달·옵션 선택 화면
- 스마트 길잡이와 세로 스크롤 안내
- QR 스캐너 및 QR 설정 팝업의 배치
- 기존 단계 전환 시 scroll-to-top 동작
- SDK의 자동 글씨 확대 및 레이아웃 관찰기

특히 기존 SDK v0.3.6에서 수정한 스크롤 안정화 구조를 훼손하지 않아야 합니다.

## 3. 방법 B — 세로 표시 영역을 줄여 하단에 배치

PoC에서 다음 세 가지 비율을 실험합니다.

- 80%: 화면의 아래쪽 80% 사용
- 70%: 화면의 아래쪽 70% 사용
- 60%: 화면의 아래쪽 60% 사용

비율은 실제 글씨 크기나 CSS transform 배율이 아니라 **사용 가능한 세로 표시 영역의 비율**입니다.

예를 들어 70%를 선택하면 화면의 위쪽 30%는 비조작 영역으로 두고, 아래쪽 70%에서 기존 키오스크 화면을 사용할 수 있게 합니다.

### 필수 요구사항

- 가로폭은 원래 키오스크 화면의 가로폭 유지
- 글씨와 버튼은 축소하지 않음
- 화면 요소의 의미와 순서 변경 없음
- 각종 메뉴·상품·가격·설명 유지
- 마지막 버튼까지 스크롤로 접근 가능
- 화면 하단을 기준으로 표시 영역 배치
- 선택한 비율이 바뀌면 표시 영역의 높이만 변경
- SDK의 큰 글씨·큰 버튼 설정과 독립적으로 작동

상단 비조작 영역에는 임의의 조작 버튼을 새로 만들지 마세요.

가능하면 상단에는 비활성 배경만 남기되, 기존 콘텐츠가 잘못 비쳐 보이거나 클릭되는 일이 없어야 합니다.

## 4. 기술 구현 원칙

단순히 전체 앱에 `transform: scale()`을 적용하는 것은 방법 B가 아니므로 금지합니다.

먼저 SDK에서 관리할 수 있는 하단 표시 영역과 내부 스크롤 컨테이너를 구성하는 방식을 검토해 주세요.

가능한 기술은 다음을 포함하되, 반드시 이 방식에 한정할 필요는 없습니다.

- 공통 SDK의 viewport shell
- 기존 호스트 root의 임시 래핑
- height / max-height / overflow 조정
- 스크롤 소유 요소를 하단 표시 영역으로 제한
- 고정 버튼·헤더의 위치 조정
- 모달과 오버레이를 하단 영역 안에서 안전하게 표시

**SDK가 특정 카페 CSS 클래스에 의존하는 구조는 피하고, 루트와 특수 영역을 어댑터에서 선택적으로 등록하는 방식을 우선 검토해 주세요.**

데모커피에서 최소한의 연결 작업은 허용하지만, 카페 화면을 통째로 전용 레이아웃으로 다시 만드는 것은 금지합니다.

호스트의 실제 DOM을 이동하거나 래핑할 경우 React의 렌더링·이벤트·포털 동작을 해치지 않는지 확인해 주세요. 위험하면 별도 실험 fixture로 먼저 검증하고 안전한 대안을 사용하세요.

## 5. 큰 글씨·큰 버튼과 동시 적용

방법 B에서 가장 중요한 조건입니다.

다음 설정 조합을 시험해 주세요.

A. 하단 70%만 적용

B. 하단 70% + 큰 글씨

C. 하단 70% + 아주 큰 글씨

D. 하단 70% + 큰 버튼

E. 하단 70% + 아주 큰 글씨 + 큰 버튼 + 고대비

F. 하단 60% + 아주 큰 글씨 + 큰 버튼

G. 하단 80% + 아주 큰 글씨 + 큰 버튼

각 조합에서 확인할 사항:

- computed font-size 실제 픽셀값
- 버튼의 실제 getBoundingClientRect 크기
- 기존과 비교한 시각적 버튼 크기
- 버튼 클릭 hit-test
- 글자 단위 줄바꿈 여부
- 내용 잘림·겹침
- 문서 가로 넘침
- 하단 조작부와 메뉴 간 충돌

방법 B 적용 전후에 글씨·버튼 크기가 유지되어야 합니다.

단순히 computed font-size만 동일한 것이 아니라 화면에서 실제로 표시되는 크기도 확인해 주세요.

## 6. 스크롤 안정성 — 최우선 회귀 검사

이전에 SDK v0.3.5에서는 스크롤을 아래로 내리면 자동으로 중간까지 튀어 올라오는 심각한 문제가 있었습니다.

SDK v0.3.6에서는 해결됐으므로, 이번 실험에서 절대 재발시키지 않아야 합니다.

검증 사항:

- 손가락 스와이프로 내부 콘텐츠 스크롤
- 최하단 도달
- 0.1초·0.5초·1초·3초 후 위치 유지
- 다시 위로 스크롤 가능
- 하단 안내 표시·숨김
- 마지막 상품·주문·결제 버튼 도달 및 실제 클릭
- 비율을 변경했을 때 스크롤 위치가 의도치 않게 튀지 않음
- 화면 단계 전환 시 정상적인 맨 위 초기화
- 같은 단계에서 사용자 스크롤 유지
- SDK 안내 UI가 레이아웃 재계산을 무한 반복하지 않음

스크롤 문제를 감추기 위해 scrollTo()를 반복 호출하거나 사용자의 스크롤 입력을 강제로 덮어쓰지 마세요.

## 7. 고정 요소·팝업·안내 검증

다음 요소가 새 표시 영역 안에서 제대로 작동하는지 확인해 주세요.

- 상단 브랜드·단계 제목
- 카테고리 좌우 이동 버튼
- 메뉴 및 상품 카드
- 옵션 선택 모달
- 장바구니 및 결제 버튼
- 주문 완료 화면
- 스마트 길잡이
- 세로 스크롤 안내
- 기존 QR 설정·카메라 팝업
- 고대비 UI

고정 요소가 상단 비조작 영역에 남거나 화면 바깥으로 튀어나오면 실패로 기록해 주세요.

안내 UI가 필수 버튼을 가리는 문제도 다시 발생하지 않아야 합니다.

특히 모달·포털·QR 카메라 화면은 실제 위치와 클릭 좌표가 일치하는지 검증해 주세요.

## 8. 테스트 방식과 PoC 범위

이번 작업은 실험이므로 우선 **정식 사용자용 QR 설정 화면을 변경하지 않고** 개발용 실험 경로 또는 독립 테스트 fixture를 통해 60%·70%·80%를 변경할 수 있도록 해 주세요.

실험 UI가 필요하다면 개발 환경에서만 사용할 수 있도록 분리하고, 일반 사용자 화면에는 노출하지 마세요.

기존 `bottomControls` 설정값과 새로운 비율 설정을 실제 중앙 서버 스키마에 추가하지 마세요.

실험용 프로필이나 테스트 옵션으로만 동작하게 합니다.

PoC가 성공할 경우 공통 SDK에 적용할 API와 QR 스키마 구조를 제안해 주세요.

PoC 결과가 좋더라도 이번 단계에서 SDK 정식 배포나 Production Publish는 하지 않습니다.

## 9. 독립 구조 검증

데모커피 외에도 최소 두 가지 독립 HTML 구조를 시험해 주세요.

- 문서 전체가 스크롤되는 키오스크
- 내부 스크롤 영역과 하단 고정 버튼이 있는 키오스크

카페 전용 클래스나 화면 이름 없이 하단 표시 영역을 적용할 수 있어야 합니다.

고정 헤더, 긴 목록, 모달, 키패드, 하단 확인 버튼을 각각 포함해 주세요.

무인민원발급기 실제 프로젝트를 수정하지 않고 별도 fixture로 검증합니다.

## 10. 성공과 실패 판정

다음 항목을 모두 충족하면 방법 B가 기술적으로 유효한 후보라고 판단합니다.

- 70% 하단 표시 영역에서 전체 업무 흐름 작동
- 글씨·버튼 크기 유지
- 스크롤 튐 없음
- 모든 필수 버튼 접근 가능
- 모달·고정 버튼 위치 정상
- QR 프로필 적용·해제 후 원상 복구
- 독립 구조에서도 같은 원리로 작동

60%나 80%에서 별도 문제가 발생하면 구체적인 원인과 개선 가능성을 보고해 주세요.

다음 상황이면 무리하게 구현하지 말고 방법 A 전환을 고려할 수 있도록 보고해 주세요.

- 호스트별로 지나치게 많은 레이아웃 재작성 필요
- 주요 고정 요소와 포털을 안전하게 다루기 어려움
- 큰 글씨·큰 버튼과의 동시 적용에서 반복적인 겹침 발생
- 스크롤 튐이나 클릭 좌표 불일치 해결 어려움
- 화면 복원에 실패
- 독립 구조에서 재사용하기 어려움
