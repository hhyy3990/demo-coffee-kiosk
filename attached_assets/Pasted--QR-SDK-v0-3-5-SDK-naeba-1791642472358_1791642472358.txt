# 내 방식 QR 공통 SDK v0.3.5 개발 — 전체 글씨 자동 확대·세로 스크롤 안내·기존 메뉴 이동 버튼 강조

현재 데모커피 프로젝트에서 공통 접근성 SDK `@naebangsik/kiosk-accessibility-sdk@0.3.4`를 개발·관리하고 있습니다.

이번 작업에서는 실제 QR 통합 테스트에서 발견한 문제들을 해결하고, 서로 다른 키오스크에서도 별도 수정 없이 최대한 재사용할 수 있도록 SDK를 개선하려고 합니다.

**핵심 목표는 다음 세 가지입니다.**

1. 키오스크의 일반 텍스트를 SDK가 자동으로 발견하고 확대
2. 세로 스크롤이 필요하면 사용자가 이를 알 수 있도록 화면 하단에 안내
3. 가로 스크롤 안내를 제거하고, 기존의 다음 메뉴 이동 버튼을 강조

이번 작업은 공통 SDK v0.3.5 개발입니다. 데모커피의 기존 주문 기능은 유지하고, 무인민원발급기 프로젝트와 중앙 서비스는 수정하지 마세요.

---

## 1. 전체 글씨 자동 확대

현재 SDK는 `getTextTargets()`에 등록된 요소를 중심으로 글씨를 확대합니다.

그러나 실제 무인민원발급기에서는 '증명서에 표시할 항목'은 확대되지만 '신청 내용 확인' 화면의 일부 글씨는 작게 남아 있었습니다.

새 키오스크마다 모든 텍스트를 하나씩 등록해야 한다면 범용 SDK의 장점이 줄어듭니다.

따라서 **명시적인 제외 대상이 아니라면 SDK가 관리하는 화면 내부의 일반 텍스트를 자동으로 찾아 확대**하도록 개선해 주세요.

### 자동 탐지 대상

- 제목 및 소제목
- 설명과 안내문
- 버튼 안의 글씨
- 상품명·가격
- 표와 목록 안의 텍스트
- 입력 필드의 레이블과 입력값
- 선택 항목·스위치 설명
- 금액·수량·단계 안내
- 결제·신청 내용 확인 화면의 요약 정보
- DOM 안에 표시되는 일반적인 한국어·영어 텍스트

특정 클래스 이름이나 키오스크 전용 구조에 의존하지 말고, SDK 루트 내부의 실제 DOM과 computed style을 기준으로 범용적으로 탐지해 주세요.

### 확대 방식

- 기존 textSize의 standard / large / extraLarge 설정 유지
- 원본 글씨 크기를 기준으로 기존 SDK 확대 비율 적용
- 상위 요소와 자식 요소에 확대가 중복 적용되지 않도록 처리
- CSS의 px, rem, em 설정에서도 실제 계산 크기를 기준으로 적용
- 화면 크기 변경 시 원래 반응형 기준으로 재계산
- 동일 프로필 재적용 시 크기가 누적되지 않음
- 화면 단계 전환으로 새 텍스트가 나타나면 자동 발견 및 적용
- `endSession()` 시 원래 스타일로 복원
- SDK가 생성한 안내 UI에는 재귀적으로 확대 적용하지 않도록 분리

버튼 안의 아이콘, SVG, QR 코드, 캔버스, 이미지 자체는 텍스트로 잘못 판단하지 마세요.

숨김 요소, 비활성 템플릿, 화면에 없는 모달 내용은 임의로 표시하거나 조작하지 마세요.

기존 `getTextTargets()`는 자동 탐지가 어려운 특수 요소를 추가하거나 예외를 지정하는 선택적 수단으로 유지해 주세요.

### 읽기 쉬운 크기와 레이아웃

기존처럼 9px 설명이 큰 글씨 모드에서 11.25px가 되는 것은 여전히 읽기 어렵습니다.

따라서 단순 배율 확대뿐 아니라, 작은 원본 글씨가 너무 작게 남지 않도록 최소 글씨 크기 정책도 실험해 주세요.

다만 모든 요소에 무조건 18px을 강제하지 말고, 일반 본문·보조 문구·버튼 등 의미별로 안전한 기준을 검토해 주세요.

최소 크기는 실제 픽셀 단위로 측정하고, 큰 글씨와 아주 큰 글씨 모드를 구분해 주세요.

텍스트 확대 때문에 다음 문제가 발생하지 않아야 합니다.

- 글자 단위로 세로 줄바꿈
- 다른 글씨와 겹침
- 내용 잘림
- 버튼 클릭 영역 축소
- 중요한 설명이나 선택지 숨김
- 화면 전체 가로 넘침

필요하면 기존 SDK의 안전한 레이아웃 보정을 이용하되, 개선되지 않으면 롤백하고 진단 결과를 남겨 주세요.

범용 SDK가 해결할 수 없는 고정 레이아웃은 조용히 무시하지 말고 구체적인 한계를 보고해 주세요.

## 2. 세로 스크롤 안내 판정 변경

현재 SDK v0.3.4는 등록된 메뉴나 주요 버튼이 화면 아래에 있을 때 안내하려고 합니다.

그러나 실제 카페와 무인민원발급기에서는 스크롤이 필요한데도 `no-safe-space` 등의 이유로 안내가 나타나지 않았습니다.

이번에는 **실제 세로 스크롤이 가능하고 아래로 더 이동할 수 있는 경우 안내를 표시하는 방식**으로 변경해 주세요.

사용자의 의도는 다음과 같습니다.

"키오스크에 세로 스크롤바가 나타나고, 아래로 스크롤해야 볼 내용이 있다면 무조건 안내해야 한다."

### 동작 조건

- `scrollHeight > clientHeight`이고 아래로 실제 이동할 수 있으면 안내
- 스크롤 끝에 도달하면 안내 숨김
- 다시 위로 이동하면 재표시
- QR 적용 후 새로 세로 스크롤이 생겨도 안내
- QR 적용 전 기본 화면에서도 안내
- 문서 전체 스크롤과 내부 컨테이너 스크롤 모두 지원
- 화면 단계 전환·크기 변경·콘텐츠 변경 후 자동 재판정
- 실제로 이동할 수 없는 `overflow: hidden` 영역에는 잘못된 안내를 표시하지 않음
- 미세한 소수 픽셀 차이 때문에 안내가 반복 점멸하지 않도록 오차 범위 적용

단순히 메뉴 개수가 몇 개인지는 표시 조건으로 사용하지 마세요.

안내 문구의 기본값:

"아래에도 내용이 있습니다. 화면을 위로 밀어보세요."

호스트가 원하면 증명서·상품 등 용도에 맞게 문구를 변경할 수 있도록 해 주세요.

## 3. 세로 안내의 하단 표시 방식 개선

기존에는 SDK가 안전한 빈 공간을 찾지 못하면 안내를 숨겼습니다.

그러나 사용자는 메뉴가 조금 가려지는 것보다 스크롤 방법을 모르는 것이 더 큰 문제라고 판단했습니다.

따라서 이번에는 **세로 스크롤이 필요한 상황에서 안내가 실제로 보이도록 배치 방식을 개선**해 주세요.

### 배치 요구사항

A. 하단 고정 조작부가 없는 키오스크

- 화면 하단에 안내
- 일반 콘텐츠 일부와 시각적으로 겹치는 것은 제한적으로 허용
- `pointer-events: none` 등으로 기존 터치·클릭을 방해하지 않음
- 스크롤 끝에서는 안내 숨김

B. 하단 고정 조작부가 있는 키오스크

- 고정된 확인·이전·처음화면 버튼 위에 안내
- 고정 버튼은 절대 가리지 않음
- 안내의 위치는 실제 버튼 영역 좌표를 기준으로 계산
- 안내와 메뉴가 겹치는 경우에도 스크롤로 메뉴에 접근할 수 있어야 함

C. 공통 사항

- 스마트 길잡이와 시각적으로 충돌하지 않도록 조정
- 헤더와 브랜드·시계 영역을 가리지 않음
- 큰 글씨·고대비에서도 안내가 읽히도록 표시
- 좁은 화면에서 안내 문구 줄바꿈 허용
- 세로 안내가 스크롤바 조작 자체를 가리지 않음
- 스크롤 끝에서 숨겨지면 마지막 메뉴와 필수 버튼을 실제로 클릭할 수 있어야 함
- 안내가 필수 조작 요소를 가리는 경우 위치 조정 또는 최소한의 스크롤 여백 확보
- 안전하게 조작할 수 없는 화면에서는 문제를 진단에 남김

기존 `no-safe-space`로 안내를 무조건 숨기는 정책을 재검토해 주세요.

필수 조작을 방해하지 않는 한 일반 스크롤 콘텐츠와의 제한적인 시각적 중첩은 허용합니다.

단, 단순히 가린 채 `pointer-events: none`만 설정하고 접근성이 해결됐다고 주장하지 마세요. 끝까지 스크롤해서 모든 필수 내용과 버튼에 접근할 수 있는지 실제로 검증해야 합니다.

## 4. 가로 스크롤 안내 기능 제거

기존 SDK v0.3.4의 `horizontalLists` 기반 가로 스크롤 안내 기능을 제거해 주세요.

다음 항목을 정리합니다.

- '오른쪽에도 메뉴가 있습니다' 등의 가로 안내 UI
- 가로 안내 표시 조건
- 세로 안내와 가로 안내의 우선순위 경쟁
- 사용하지 않는 관련 타입·테스트·README 설명

기존 키오스크의 가로 스크롤 동작 자체를 차단하거나 수정하지 마세요.

이번에는 가로 목록에 새로운 버튼을 생성하지 않습니다.

## 5. 기존 다음 메뉴 이동 버튼 강조

가로 스크롤 안내 대신, 키오스크에 이미 존재하는 **'다음 항목 또는 다음 메뉴를 보여주는 버튼'을 강조하는 기능**을 개발해 주세요.

중요한 것은 화살표 모양 자체가 아니라 **버튼이 실제로 다음 항목으로 이동시키는 역할을 하는지**입니다.

### 탐지 방식

가능하면 다음 정보를 활용해 자동 탐지해 주세요.

- 버튼의 접근성 이름 (`aria-label`)
- `aria-controls`로 연결된 목록
- '다음 메뉴', '다음 카테고리', '다음 항목 보기' 등의 의미
- 버튼의 활성·비활성 상태
- 목록의 현재 스크롤 위치 및 다음 항목 존재 여부

명확하게 확인할 수 없는 버튼을 임의로 다음 버튼이라고 판단하지 마세요.

필요하면 호스트 어댑터가 기존 버튼을 선택적으로 등록할 수 있도록 해 주세요.

특히 일반적인 '다음 단계', '결제', '주문 확정' 버튼을 카테고리 이동 버튼으로 잘못 인식해서는 안 됩니다.

### 강조 동작

- 실제로 이동할 다음 항목이 있을 때만 강조
- 끝에 도달하거나 버튼이 비활성화되면 강조 해제
- 기존 버튼의 테두리·배경·윤곽선 등으로 시각적 강조
- 고대비 모드에서도 식별 가능
- 강조 표시가 버튼 클릭을 방해하지 않음
- SDK가 버튼을 자동으로 누르거나 새로운 버튼을 생성하지 않음
- 버튼의 원래 동작·레이블·포커스 상태 유지
- 화면 전환 및 세션 종료 시 강조 상태 정리

이번에 데모커피에는 좌우 카테고리 화살표 버튼이 추가되어 있습니다.

각 버튼은 다음 속성을 사용합니다.

- `aria-label="이전 카테고리 보기"`
- `aria-label="다음 카테고리 보기"`
- `aria-controls`로 카테고리 목록 연결
- 처음과 끝에서 `disabled` 처리
- 모바일 화면에서는 최소 44×44px 터치 영역

SDK가 기존 버튼을 인식해 강조하는지 데모커피 실제 화면에서 검증해 주세요.

SDK에서 새 화살표를 만들면 안 됩니다.

## 6. 자동 탐지 중심의 SDK 구조

전체 글씨 확대와 세로 스크롤 감지, 다음 메뉴 버튼 강조 모두 다음 원칙으로 설계해 주세요.

**자동 탐지를 기본으로 하고, 자동 탐지가 불확실한 경우에만 키오스크 어댑터로 보완합니다.**

- 특정 카페·민원발급기 CSS 클래스에 의존하지 않기
- DOM과 실제 계산된 스타일을 이용해 범용 탐지
- 기존 어댑터 API와의 호환성 유지 가능한 범위 확인
- 자동 탐지와 명시적 등록이 중복되면 한 번만 적용
- SDK 루트 밖의 요소를 임의로 수정하지 않기
- 페이지 전체를 과도하게 반복 탐색해 성능 저하를 일으키지 않기
- MutationObserver·ResizeObserver 사용 시 무한 재측정과 누적 확대 방지
- 기존 SDK 자체 안내 UI를 탐지·확대 대상으로 잘못 포함하지 않기

프로필이 제거되면 SDK가 적용한 스타일과 이벤트를 원래대로 정리해야 합니다.

## 7. 독립 Chromium fixture 검증

서로 다른 HTML 구조에서 다음을 검증해 주세요.

A. 고정 px 글씨와 rem 글씨가 혼합된 화면

B. 제목·설명·표·금액·선택 스위치가 있는 신청 화면

C. 이미지·상품명·가격·설명이 포함된 복합 버튼

D. 문서 전체가 세로 스크롤되는 키오스크

E. 내부 컨테이너가 세로 스크롤되는 키오스크

F. 하단 고정 조작 버튼이 있는 화면

G. 가로 화살표 버튼이 있는 카테고리 목록

H. 가로 스크롤만 있고 기존 화살표 버튼이 없는 목록

I. 큰 글씨·큰 버튼 적용 후 새로 세로 스크롤이 생기는 화면

J. 스크롤이 불가능하거나 항목이 모두 보이는 화면

각 구조에서 다음을 확인합니다.

- 자동 확대된 텍스트 비율
- 확대되지 않은 텍스트와 그 이유

이번 버전의 가장 중요한 성공 기준은 다음과 같습니다.

**첫째, 무인민원발급기에서 '신청 내용 확인' 같은 화면의 글씨를 하나씩 등록하지 않아도 확대할 수 있는 범용 엔진을 만드는 것.**

**둘째, 실제 세로 스크롤이 필요한 화면에서는 안내가 사라지지 않고 나타나며, 사용자가 끝까지 스크롤해 필수 버튼을 누를 수 있는 것.**

**셋째, 기존 카테고리 이동 버튼은 새로운 버튼 생성 없이 SDK가 강조하고, 원래 조작 방식과 업무 흐름을 변경하지 않는 것.**
