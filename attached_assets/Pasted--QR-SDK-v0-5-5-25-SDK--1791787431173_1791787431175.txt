# 내 방식 QR — SDK v0.5.5 최종 검증: 스크롤 실패 25건 원인 해결 및 조건부 릴리스

현재 데모커피 프로젝트에서 공통 접근성 SDK를 개발하고 있습니다.

현재 공개 버전은 v0.5.4이며, 다음 수정이 SDK 소스에 반영된 상태입니다.

- 하단 60·70·80% viewport 지원
- QR 프로필 v3 자동 적용
- QR 하단 도크
- 스크롤 안내 및 스마트 길잡이
- notifyScreenChange() 화면 전환 API
- 큰 min-height와 세로 중앙 정렬이 결합될 때 상단 콘텐츠가 잘리는 문제를 방지하는 안전 중앙 정렬 수정

마지막 수정으로 1440×900에서 발생하던 상단 제목 잘림이 해결됐으며, 독립 fixture 103개 조합에서 제목 잘림은 0건입니다.

그러나 103개 중 25개 조합에서 마지막 버튼 표시·클릭 검사가 실패했습니다.

분석 결과 실패한 25개 모두 실제 스크롤 영역의 scrollTop이 최대값에 도달하기 전에 테스트가 종료됐습니다.

예를 들어 어떤 조합에서는 최대 스크롤 거리 906px 중 73px만 이동했습니다.

따라서 현재는 실제 SDK 스크롤 결함인지, 브라우저 자동화 입력이 충분하지 않았던 것인지 판정할 수 없습니다.

이번 작업은 **이 25개 사례의 원인을 명확히 판정하고, 모든 필수 검증을 통과한 경우에만 SDK v0.5.5를 제작하는 것**입니다.

## 1. 기존 수정 보존

우선 기존 SDK 코드와 테스트를 확인해 주세요.

특히 안전 중앙 정렬 수정은 보존합니다.

- 기존 103개 fixture 유지
- 실패한 25개 조합 유지
- 테스트 조건 및 합격 기준 유지
- 기존 v0.5.4 tarball 보존
- 원인 확인 전 SDK 로직 변경 금지

무인민원발급기 프로젝트는 수정하지 않습니다.

## 2. 실제 스크롤 소유자 확인

25개 실패 사례에서 실제로 스크롤되는 요소를 다시 확인합니다.

측정 항목:

- document.scrollingElement
- SDK 등록 scrollArea
- 실제 내부 스크롤 요소
- scrollTop
- scrollHeight
- clientHeight
- 최대 scrollTop
- overflow-y
- pointer-events
- touch-action
- 스크롤 이벤트 발생 횟수
- 스크롤 중 높이·위치 변화

스크롤 이벤트를 보냈는데 scrollTop이 증가하지 않는다면, 왜 증가하지 않는지 조사해 주세요.

실제 스크롤 영역이 아닌 바깥 컨테이너에 입력하고 있었는지도 확인합니다.

## 3. 실제 휠 입력 검증

데스크톱 브라우저에서는 실제 사용자와 유사한 휠 입력을 반복합니다.

- 스크롤 컨테이너 안쪽에 입력 좌표 지정
- 실제 wheel 이벤트 사용
- 한 번만 휠 입력하고 종료하지 않기
- scrollTop 증가량 측정
- 여러 번 반복해 실제 최대 스크롤 지점까지 이동
- 더 이상 이동할 수 없는 상태인지 확인

스크롤이 완전히 멈춘 상태에서도 scrollTop이 최대값보다 작다면 실제 스크롤 장애 가능성이 있습니다.

다만 단일 wheel 이벤트가 충분한 이동량을 만들지 않았다는 이유만으로 실패 처리하지 마세요.

## 4. 모바일 터치 스와이프 검증

320px·360px·390px 모바일 너비에서는 Chromium 터치 에뮬레이션을 사용해 실제 사용자와 유사한 스와이프를 반복합니다.

- 실제 스크롤 영역 안에서 터치 시작
- 위쪽 방향으로 여러 번 스와이프
- 매 스와이프 후 scrollTop 기록
- 마지막 버튼이 보일 때까지 진행
- 버튼이 보이면 실제 터치 탭
- 클릭 이벤트 실행 확인
- 화면을 다시 위로 스와이프해 제목 접근 확인

단순히 touch 이벤트를 JavaScript로 dispatch하는 것과 브라우저가 실제 스크롤을 처리하는 터치 입력은 구분해 주세요.

터치 에뮬레이션이 제대로 작동하지 않는다면 이를 실제 SDK 결함으로 오인하지 말고, 테스트 방법의 한계를 보고해 주세요.

## 5. 강제 최대 스크롤 진단

실제 휠·터치 테스트와 별개로, 레이아웃 자체를 조사하기 위한 진단을 수행합니다.

실제 스크롤 소유자에 다음과 같은 방식으로 최대 위치를 적용해 주세요.

`scrollTop = scrollHeight - clientHeight`

이것은 진단용이며 실제 사용자 접근성 합격을 대신하지 않습니다.

진단 후 다음을 확인합니다.

- 실제 최대 scrollTop 도달 여부
- 마지막 버튼 전체 표시 여부
- QR 도크 및 고정 하단 버튼과 겹침 여부
- 마지막 버튼 중앙과 가장자리 hit-test
- 실제 클릭 이벤트
- 0.1초·0.5초·1초·3초 후 위치 유지

이를 통해 다음 두 문제를 구별합니다.

A. 강제로 최대 위치로 이동하면 정상인데 실제 입력은 도달하지 못함

B. 강제로 최대 위치로 이동해도 마지막 버튼이 잘리거나 가려짐

A라면 입력 처리나 테스트 자동화 문제를 우선 조사하고, B라면 실제 레이아웃 결함을 조사해 주세요.

## 6. 실패 원인 분류와 수정

25개 사례를 다음 기준으로 분류해 주세요.

**테스트 구현 문제**

- 스크롤 입력 횟수 부족
- 실제 스크롤 소유자에 입력하지 않음
- 터치 에뮬레이션 설정 오류
- 비동기 스크롤 완료 전에 측정
- 오래된 버튼 좌표를 사용한 클릭

이 경우 테스트를 올바르게 수정하되, 합격 기준은 낮추지 않습니다.

**공통 SDK 결함**

- 스크롤 입력을 SDK가 가로챔
- 레이아웃 보정이 scrollTop을 계속 되돌림
- 잘못된 scrollArea 등록·측정
- 실제로 스크롤 끝까지 도달할 수 없음
- 최대 위치에서도 콘텐츠가 잘림
- QR 도크나 고정 조작부가 마지막 버튼을 가림

이 경우 범용 SDK에서 수정합니다.

특정 데모커피나 무인민원발급기에만 맞는 CSS는 금지합니다.

**호스트·fixture 계약 문제**

- fixture가 SDK에 잘못된 scrollArea를 제공
- 독립 HTML의 overflow 구조가 SDK 계약과 일치하지 않음
- 실제 호스트가 필요한 어댑터 정보를 누락

이 경우 계약을 올바르게 연결하고, 다른 키오스크도 활용할 수 있도록 문서화해 주세요.

수정 이유와 전후 측정값을 반드시 보고합니다.

## 7. 기존 103개 조합 재검증

문제를 분석하고 필요한 수정을 마친 뒤 기존 103개 조합을 모두 재실행합니다.

- 하단 마지막 버튼 접근 성공
- 실제 휠 또는 브라우저 터치 스와이프로 접근 성공

## 8. 화면 전환 API 전체 회귀

SDK v0.5.4의 notifyScreenChange() 기능을 다시 검증합니다.

- 일반 화면 → 다른 업무 화면
- QR 도크 첫 화면 → 업무 화면
- 업무 화면 → QR 도크 첫 화면
- document 스크롤 ↔ 내부 스크롤 전환
- 하단 60·70·80% 활성 상태에서 화면 전환
- 다음 화면의 첫 제목 표시
- 같은 screenId 반복 전달 시 스크롤 유지
- 모달 열기·닫기 시 스크롤 유지
- 화면 전환 후 사용자의 직접 스크롤 보존
- endSession() 이후 첫 화면 상단 복귀

새 안전 정렬 수정으로 화면 전환 동작이 달라지지 않았는지 확인합니다.
