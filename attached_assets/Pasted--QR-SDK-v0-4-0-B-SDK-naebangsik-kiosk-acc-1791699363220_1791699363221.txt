# 내 방식 QR — 공통 SDK v0.4.0 개발: 방법 B 하단 조작 모드 정식 통합

현재 데모커피 프로젝트에서는 공통 접근성 SDK `@naebangsik/kiosk-accessibility-sdk@0.3.6`을 관리하고 있습니다.

최근 개발 전용 PoC에서 방법 B 하단 조작 모드를 실험했습니다.

방법 B는 화면 전체를 축소하지 않고, 글씨와 버튼 크기를 유지하면서 키오스크의 아래쪽 60%·70%·80% 영역에서 화면을 조작할 수 있도록 하는 방식입니다.

기존 PoC에서 다음 사항이 검증됐습니다.

- 하단 60%·70%·80% 영역 적용
- 큰 글씨·큰 버튼·고대비 동시 적용
- 70% 화면에서 전체 주문 과정 완료
- 스크롤 최하단 도달 후 3초간 위치 유지
- 별도 120px 안내 슬롯 제거 및 작은 pill 오버레이 적용
- 실제 하단 고정 버튼을 고려한 안내 위치 계산
- 스마트 길잡이 표시 중 스크롤 안내 숨김
- 독립 HTML 구조 fixture 검증

이번 작업의 목적은 이 PoC를 정리해 **다른 키오스크에서도 설치해 사용할 수 있는 공통 SDK v0.4.0**으로 만드는 것입니다.

단, 현재의 중앙 QR 프로필 스키마는 변경하지 않으며, 실제 무인민원발급기 프로젝트도 이번에는 수정하지 않습니다.

## 1. 기존 PoC 코드와 일반 모드 회귀 검사

정식 통합 전에 기존 SDK 소스와 PoC 변경사항을 확인해 주세요.

특히 다음 파일을 검토합니다.

- `bottom-viewport-poc.ts`
- `scroll-guidance.ts`
- `accessibility-sdk.ts`
- `styles.css`
- 데모커피 접근성 어댑터
- 독립 fixture 코드

PoC에서 공통 SDK 소스를 변경한 부분이 일반 키오스크 화면에도 영향을 주는지 먼저 확인해 주세요.

### 반드시 검증할 사항

하단 조작 모드를 활성화하지 않은 경우:

- 기존 전체 화면 레이아웃 유지
- 기존 문서 스크롤 유지
- SDK v0.3.6에서 해결한 스크롤 튐 오류 재발 없음
- 일반 화면에서 스크롤 안내 정상 표시·숨김
- 스마트 길잡이 정상 표시
- 버튼 강조 5초 동작 유지
- 글씨·버튼 자동 확대 정상 작동
- 주문·결제 및 세션 초기화 정상
- 기존 QR v1/v2 처리 유지

**하단 조작 모드를 사용하지 않는 사용자의 화면은 기존과 동일하게 작동해야 합니다.**

## 2. 방법 B를 공통 SDK 기능으로 정식 통합

개발용 `bottom-poc` 기능을 재사용 가능한 공통 SDK API로 정리해 주세요.

### 기본 동작

- 전체 화면 비례 축소 금지
- 글씨·버튼 표시 크기 유지
- 가로폭 유지
- 화면의 아래쪽 일정 비율에 표시 영역 생성
- 해당 영역 안에서 전체 콘텐츠 스크롤 가능
- 고정 헤더·하단 버튼·모달을 안전하게 처리
- 기존 업무 화면과 콘텐츠 순서 유지
- 세션 종료 시 원래 화면으로 복원

### 지원 비율

- 60%
- 70%
- 80%

70%를 향후 기본값 후보로 사용하되, 이번 SDK에서 명시적 설정이 없는 사용자에게 임의로 하단 모드를 적용하지 마세요.

### SDK 설정 인터페이스

중앙 QR 스키마를 지금 변경하지 않고도 독립 테스트에서 다음과 같은 형태를 전달할 수 있도록 설계해 주세요.

예시:

```ts
{
  mode: "bottom",
  heightPercent: 70
}
```

정확한 API 타입과 필드명은 기존 SDK 구조에 맞게 정하되, 다음 규칙을 지켜 주세요.

- `heightPercent`는 60 | 70 | 80만 허용
- 유효하지 않은 비율은 안전하게 거부하거나 기존 화면 유지
- 현재 QR의 `bottomControls: true`만으로 새 방법 B가 자동 활성화되지 않도록 처리
- 기존 `bottomControls`의 레거시 동작과 새 기능을 구분
- 명시적인 방법 B 활성화 옵션이 있을 때만 적용
- 향후 중앙 QR에 비율 필드를 추가할 때 SDK 내부 구조를 다시 설계할 필요가 없도록 구성

현재 v1/v2 QR 프로필과의 하위 호환성을 유지해야 합니다.

## 3. 범용 viewport 구조

데모커피에서 검증한 방법 B는 기존 `.kiosk` 루트를 하단 고정 스크롤 shell로 바꾸는 구조였습니다.

정식 SDK에서는 `.kiosk` 같은 카페 전용 CSS 선택자에 의존하지 않도록 해 주세요.

### 권장 구조

- 호스트가 키오스크의 최상위 화면 루트를 SDK에 등록
- SDK가 해당 루트에 하단 viewport 적용
- 필요한 경우 호스트가 고정 하단 조작부를 선택적으로 등록
- 모달·키패드·카메라·오버레이 등 특별한 요소는 어댑터로 등록 가능
- 기존 React DOM 자식 노드를 강제로 옮기거나 재구성하지 않음

자동으로 안전하게 처리할 수 있는 요소는 SDK가 처리하되, 고정 요소의 역할이 불명확한 경우에는 선택적 어댑터 등록을 사용해 주세요.

호스트가 모든 텍스트와 버튼을 일일이 등록해야 하는 구조는 피해야 합니다.

### 원상 복구

- QR 세션 종료 시 viewport 해제
- 기존 루트의 CSS 및 스크롤 속성 복원
- 고정 요소와 모달 위치 복원
- SDK 안내 UI 및 타이머 정리
- 다음 QR 프로필을 같은 SDK 인스턴스에 다시 적용 가능
- 반복 적용해도 높이·위치·확대 배율이 누적되지 않음

## 4. 작은 오버레이형 세로 안내 유지

PoC에서 기존 120px 안내 슬롯을 제거하고 작은 pill 오버레이를 적용했습니다.

정식 SDK에서도 이 방식을 유지해 주세요.

### 안내 문구

- `↓ 아래에도 내용이 있어요`
- `↓ 아래에도 버튼이 있어요`

카페·병원·은행·무인민원발급기 모두 사용할 수 있는 두 문구입니다.

### 표시 조건

- 실제로 아래로 스크롤 가능하면 표시
- 최하단에 도달하면 숨김
- 다시 위로 스크롤하면 재표시
- 주요 버튼이 아래쪽에 있는 것이 확인되면 버튼 안내
- 판단이 불확실하면 내용 안내
- 모달이 열려 있어 안내가 방해된다면 일시적으로 숨김

### 위치

- 일반 콘텐츠와 제한적으로 겹치는 것은 허용
- 필수 조작 버튼은 가리지 않음
- 하단 고정 조작부가 있다면 해당 조작부 위에 표시
- 공간이 부족하면 필수 버튼을 가리는 대신 안내를 숨김
- 안내가 스크롤 컨테이너의 크기를 변경하지 않음
- 안내 표시·숨김이 기존 스크롤 좌표를 변경하지 않음
- 큰 글씨·고대비에서도 읽을 수 있도록 처리

기존 일반 화면에서도 안내가 잘 동작해야 하며, 하단 모드에서만 사용할 수 있는 전용 안내 로직으로 분리하지 마세요.

## 5. 스마트 길잡이와 스크롤 안내 우선순위

스마트 길잡이와 스크롤 안내는 동시에 표시하지 않습니다.

### 동작

1. 스크롤이 가능하면 작은 안내 pill 표시
2. 설정한 10·15·20초 동안 조작이 없으면 스마트 길잡이 표시
3. 스마트 길잡이가 나타나면 스크롤 안내 숨김
4. 스마트 길잡이가 사라지면 스크롤 위치 재판정
5. 아래로 이동할 내용이 남았다면 스크롤 안내 복귀
6. 최하단에 도달했다면 스크롤 안내 미표시

스마트 길잡이의 카드 크기와 가독성을 유지하되, 기존 고정 버튼이나 키패드 등을 가리지 않도록 해 주세요.

안전한 표시 위치가 없으면 사용자의 필수 조작을 막지 않는 방향으로 처리하고, 진단에 그 이유를 남겨 주세요.

스마트 길잡이가 표시되지 못한 채 무기한 반복 대기하는 상황이 없는지도 검증해 주세요.

## 6. 큰 글씨·큰 버튼과의 독립성

방법 B의 주요 장점은 화면을 아래로 옮겨도 글씨와 버튼을 축소하지 않는 것입니다.

다음 조합에서 이를 확인해 주세요.

- 하단 60% + 기본 글씨
- 하단 70% + 큰 글씨
- 하단 70% + 아주 큰 글씨
- 하단 70% + 큰 버튼
- 하단 70% + 아주 큰 글씨 + 큰 버튼 + 고대비
- 하단 60% + 아주 큰 글씨 + 큰 버튼 + 고대비
- 하단 80% + 아주 큰 글씨 + 큰 버튼 + 고대비

각 조합에서 다음을 실제 픽셀값으로 측정합니다.

- computed font-size
- 실제 렌더링 글씨 크기
- 버튼 bounding rectangle
- 버튼 hit-test
- 글씨 잘림·겹침 여부
- 문서 가로 넘침
- 필수 메뉴·버튼 도달 가능 여부

방법 B 활성화 전후 글씨와 버튼 크기가 동일해야 합니다.

## 7. 스크롤 안정성 검증

이전에 SDK v0.3.5에서 발생했던 스크롤 튐 오류가 절대 재발해서는 안 됩니다.

### 검사 항목

- 실제 스크롤 소유 요소 확인
- 최하단 scrollTop 측정
- 0.1초·0.5초·1초·3초 후 위치 측정
- 스크롤 안내 표시·숨김
- 스마트 길잡이 표시·숨김
- 화면 단계 전환 시 정상적인 상단 초기화
- 같은 단계에서 사용자 스크롤 위치 유지
- 비율 변경 시 정상 재계산
- 반복 활성화·해제 시 누적 변형 없음
- 마지막 주문·결제 버튼의 실제 클릭 성공

SDK가 사용자의 스크롤 위치를 반복해서 강제로 설정하는 방식은 금지합니다.

## 8. 독립 소비자 프로젝트 검증

정식 SDK의 범용성을 검증하기 위해 카페 프로젝트 외에 독립적인 HTML 구조 두 가지 이상에서 테스트해 주세요.

### A. 문서 전체 스크롤 구조

실제 `document.scrollingElement`가 스크롤을 소유하는 구조를 포함해 주세요.

PoC에서 최상위 콘텐츠 래퍼 스크롤만 검증했던 한계를 보완해야 합니다.

### B. 내부 스크롤 + 하단 고정 조작부

- 긴 목록
- 고정 헤더
- 고정 하단 버튼
- 키패드
- 모달
- QR 또는 카메라 영역을 모사한 overlay

각 구조에서 60%·70%·80%를 검증합니다.

호스트 전용 CSS를 과도하게 추가하지 않고도 SDK API와 최소 어댑터 연결로 작동해야 합니다.

실제 무인민원발급기 프로젝트는 이번 단계에서 수정하지 마세요.

## 10. SDK 버전과 패키지 제작

이번 정식 기능을 SDK `0.4.0`으로 출시할 수 있도록 버전을 업데이트해 주세요.

버전은 반드시 npm이 허용하는 SemVer 형식이어야 합니다.

다음 tarball을 제작합니다.

`packages/kiosk-accessibility-sdk/releases/naebangsik-kiosk-accessibility-sdk-0.4.0.tgz`

기존 v0.1.0~v0.3.6 아카이브는 보존합니다.

### 필수 검사

- SDK 타입 검사
- SDK 단위 테스트
- Chromium fixture
- 데모커피 주문 회귀 테스트
- 독립 소비자 tarball 설치
- 소비자 TypeScript 검사
- 소비자 프로덕션 빌드
- QR v1/v2 호환성
- 기존 스마트 길잡이·음성 안내·세션 초기화

특히 **실제 tarball을 새 독립 소비자에 설치한 뒤 기능을 검증**해야 합니다. 카페 프로젝트에서 소스 코드를 직접 import한 테스트만으로 성공이라고 판단하지 마세요.
