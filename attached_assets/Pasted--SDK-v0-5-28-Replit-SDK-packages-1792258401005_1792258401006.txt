# 공통 SDK v0.5.28 — 쉬운 말 안내 공간 최적화 및 스크롤 안내 위치 복구

현재 프로젝트는 **데모커피 Replit**입니다.

공통 SDK 원본:
`packages/kiosk-accessibility-sdk/`

이번 작업은 사용자가 실제 무인민원발급기 화면에서 발견한 두 문제를 해결하기 위한 **기존 기능 수정**입니다.

1. 쉬운 말 안내의 페이지가 과도하게 많아지고 단어·짧은 구절 단위로 분할되는 문제
2. 기본 화면 모드에서 하단 스크롤 안내가 고정 조작 버튼과 겹치는 문제

사용자는 공간이 부족한 경우 안내창 내부 버튼, 글씨 크기, 간격을 소폭 조정하는 것을 허용했습니다.

**다만 새로운 기능, 키오스크 업무 로직, 전체 디자인은 변경하지 마세요.**

## 1. 쉬운 말 안내의 실제 문제

무인민원발급기에서 주민등록표 종류 선택 화면의 쉬운 말 안내가 `1/21`까지 나뉘고 첫 페이지에는 `주민등록표` 한 단어만 표시됐습니다.

실제 안내 데이터:

stepId: `certificate.type-selection`

항목 1:
- 제목: 주민등록표 등본
- 본문: 주민등록표 등본은 한 세대의 구성과 주소 정보를 확인하는 주민등록 서류입니다.

항목 2:
- 제목: 주민등록표 초본
- 본문: 초본 발급은 아직 준비 중입니다. 이 데모에서는 등본만 진행할 수 있습니다.

이후 무인민원발급기 Preview에서 같은 데이터로 측정한 결과는 다음과 같습니다.

- 390×844 자동 하단 80%: 2페이지
- 320×844 자동 하단 80%: 4페이지
- 360×667 자동 하단 80%: 6페이지
- 과거 사용자 실제 화면: 21페이지

21페이지 상태의 정확한 재현 조건은 아직 특정되지 않았습니다.

**21페이지가 재현되지 않았다는 이유만으로 문제를 해결했다고 보고하지 마세요.**

## 2. 쉬운 말 안내창의 공간 활용 개선

사용자가 실제 사진에서 지적한 사항은 다음과 같습니다.

- 안내창 위쪽과 아래쪽에 여유 공간이 보임
- 무인민원발급기에서는 이전·다음 버튼이 본문 아래 별도 줄에 위치함
- 데모커피에서는 좁은 화면에서 이전·다음 버튼을 접기·펼치기 버튼 옆에 배치하는 경우가 있음
- 별도 버튼 줄 때문에 본문에 사용할 공간이 줄어들 가능성이 있음

### A. 이전·다음 버튼 배치

좁은 화면에서 먼저 **데모커피의 기존 한 줄 조작부 배치가 어떤 조건에서 동작하는지** 확인하세요.

가능하면 같은 공통 SDK 배치를 무인민원발급기의 긴 제목에도 적용하세요.

목표:
- 이전·다음·접기/펼치기를 상단 조작 영역에 함께 배치
- 페이지 번호도 가독성 있게 표시
- 버튼 때문에 본문 아래에 별도의 44px 줄이 생기는 현상 최소화
- 제목과 버튼이 겹치지 않음
- 필요한 경우 제목 영역과 조작부의 폭·줄바꿈을 합리적으로 조정

단, 제목을 잘라내거나 버튼을 화면 밖으로 밀어내지 마세요.

가로폭이 부족해 한 줄 배치가 불가능한 경우에는 기존보다 세로 공간을 적게 쓰는 대안을 실제 DOM 측정으로 검토하세요.

### B. 안내창 높이

안내창이 실제로 사용할 수 있는 상단 공간을 다시 측정하세요.

- 화면 상단과 안내창 사이 간격
- 안내창 하단과 업무 영역 시작 지점 사이 간격
- 패널 최대 높이 제한
- 실제 상단 20% 안전 영역
- 헤더·본문·조작부 높이
- 상하 padding과 gap

안내창 상단 Y=8px 고정 원칙은 유지합니다.

**업무 영역이나 하단 80%를 줄이지 않는 범위에서 실제 사용 가능한 공간을 최대한 활용하세요.**

스크린샷에서 보이는 틈이 실제 안전 여백인지, SDK 최대 높이 제한인지 구분해야 합니다.

안내창을 아래로 확장하더라도 업무 화면을 가리거나 버튼 클릭을 방해하지 않아야 합니다.

### C. 추가 공간 최적화

사용자는 정말 공간이 부족하다면 다음을 허용했습니다.

- 불필요한 padding·gap 축소
- 글자 간격·줄 간격 조정
- 쉬운 말 안내창 내부 글씨 크기 소폭 축소
- 안내창 조작 버튼의 시각적 크기 소폭 축소

우선 기존 44×44px 터치 영역을 유지하세요.

버튼의 시각적 크기를 줄이더라도 터치 영역은 가능한 한 유지하고, 사용하기 어려운 작은 버튼을 만들지 마세요.

매우 큰 글씨 설정의 의미가 사라질 정도로 글씨를 축소하지 마세요.

**안내 원문은 이번 작업에서 변경하지 마세요.** 문구 수정이 꼭 필요하다면 수정안을 제시하고 사용자 승인을 기다리세요.

## 3. 쉬운 말 페이지 분할 안정화

레이아웃을 최적화한 뒤 실제 본문 공간을 기준으로 페이지를 다시 계산하세요.

필수 조건:

- 한 글자씩 분할하지 않음
- 한 단어씩 연속적으로 분할하지 않음
- 가능한 한 문장·의미 단위로 표시
- 원문 누락·중복 없음
- 제목·본문 잘림 없음
- 페이지 이동 중 총 페이지 수가 이유 없이 변하지 않음
- 접기·펼치기 후 다시 열었을 때 정상적인 페이지 구성 유지
- 스마트 길잡이 종료 후 원래 쉬운 말 페이지·접힘 상태 복원
- 무한 재귀 없음
- 상단 패널 위치 점프 없음

특히 헤더와 이전·다음 버튼이 나타났다 사라지면서 본문 높이 계산이 반복되는 문제를 방지하세요.

### 페이지 수 검증

다음 화면에서 실제 페이지 수와 각 페이지 텍스트를 기록하세요.

- 320×844
- 360×667
- 390×844
- 1080×1920

설정:
- textSize: extraLarge
- buttonSize: large
- contrast: high
- easyLanguage: true
- viewportMode: null → 자동 하단 80%

추가로 명시적 80%, 60%, 일반 모드도 관련 회귀를 확인하세요.

**목표는 360×667에서도 한 페이지에 두 줄 이상 표시할 공간을 확보하고, 현재 6페이지보다 페이지 수를 합리적으로 줄이는 것입니다.**

다만 원문 보존과 실제 가독성을 해치면서 임의의 페이지 수에 맞추지 마세요.

2~4페이지 정도를 우선적인 개선 목표로 검토하되, 실측으로 불가능하면 근거를 보고하세요.

실제 한 줄만 들어가는 화면을 2줄로 들어간 것처럼 계산하거나 overflow:hidden으로 감추는 방식은 금지합니다.

## 4. 스크롤 안내 위치 문제

현재 무인민원발급기의 호스트 연결 정보는 다음과 같습니다.

파일: `src/useKioskAccessibility.ts`

호스트는 `getLayoutRegions()`에서 다음 요소들을 SDK에 등록합니다.

- scrollArea → `main.stage`
- bottomControls → `.device-footer[data-a11y-slot="bottom-controls"]`

현재 SDK의 스크롤 안내는 선택적인 `[data-a11y-slot="above-bottom-controls"]` 요소를 기준으로 장애물을 계산하지만, 호스트에서 전달하는 `bottomControls` 배열은 스크롤 안내 좌표 계산에 직접 반영되지 않는 것으로 확인됐습니다.

### 실제 기본 모드 측정

390×844:

- 실제 스크롤 owner: Document
- footer: y=758~844
- 처음화면 버튼: y=793~836
- 전화면 버튼: y=793~836
- 스크롤 안내: y=787.61~832
- 안내 inline bottom: 12px

따라서 기본 모드에서 스크롤 안내가 두 버튼과 실제로 겹칩니다.

### 실제 하단 80% 측정

- scroll owner: `.stage`
- footer 상단: y=758
- 스크롤 안내: y=701.61~746
- footer와 간격: 12px
- 버튼 겹침 없음

### 수정 목표

**공통 SDK가 기존 `bottomControls` 등록 정보를 실제 스크롤 안내 위치 계산에도 반영하도록 최소 수정하세요.**

- 기본 모드에서도 하단 고정 조작부 위쪽에 안내 표시
- footer 상단과 약 12px 간격 유지
- 하단 80% 모드의 정상 위치 유지
- 하단 60·70% 모드 유지
- 스크롤 중 위치 점프 없음
- 스크롤 끝에서 안내 숨김
- `pointer-events:none` 유지
- 업무 버튼 조작 방해 없음
- 데모커피의 주문 확인 바 위쪽 배치 유지

고정 하단 조작부가 없는 키오스크에서는 기존 위치가 불필요하게 바뀌지 않아야 합니다.

모든 `bottomControls`가 항상 고정 요소인 것은 아니므로 실제 위치·표시 상태·스크롤 영역과의 관계를 확인한 뒤 반영하세요.

**호스트에 새 슬롯을 강제로 추가하거나 CSS 하드코딩으로 해결하지 마세요.**

## 5. SDK 소비자 fixture 구성

데모커피와 무인민원발급기의 실제 호스트 레이아웃이 다를 수 있다는 점을 고려하세요.

무인민원발급기 재현 fixture는 다음 구조를 반영해야 합니다.

- `main.stage`가 SDK의 scrollArea로 등록됨
- 모바일 기본 모드에서는 Document가 실제 scroll owner
- 하단 80%에서는 `.stage`가 실제 scroll owner
- `.device-footer`가 하단 고정 조작부로 등록됨
- footer 안에 처음화면·전화면 버튼 존재
- 실제 쉬운 말 설명 배열은 항목별 title/text로 전달
- 매우 큰 글씨, 큰 버튼, 고대비 적용

가능하면 실제 호스트와 비슷한 헤더·footer 크기 및 세로 레이아웃을 재현하세요.

독립 fixture에서 통과하더라도 무인민원발급기 실제 프로젝트에서는 별도 확인이 필요하다고 명시하세요.

## 6. 스마트 길잡이 기존 동작 보호

다음 기능은 이미 실제 무인민원발급기에서 검증됐습니다.

- 360×667 결제 안내 67자 → 2페이지
- 일반 2페이지 → 총 15초, 약 7.5초에 전환
- 느린 안내 2페이지 → 총 20초
- 일반 1페이지 → 10초
- 스마트 길잡이 헤더 44px
- 안내창 상단 약 8px 유지
- 종료 후 쉬운 말 접힘 및 페이지 복원

**이번 쉬운 말 안내 배치 수정이 스마트 길잡이의 표시 구조와 시간 정책에 영향을 주면 안 됩니다.**

같은 CSS 클래스를 공유하는 경우에는 변경 범위를 명확히 분리하고 회귀 테스트로 확인하세요.
