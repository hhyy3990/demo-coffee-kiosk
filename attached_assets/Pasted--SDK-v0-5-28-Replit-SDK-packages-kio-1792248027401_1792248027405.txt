# 공통 SDK v0.5.28 — 작은 화면 스마트 길잡이 공간 부족 원인 진단

현재 프로젝트는 **데모커피 Replit**입니다.

공통 SDK 경로:
`packages/kiosk-accessibility-sdk/`

이번 작업은 스마트 길잡이 안내창의 공간 부족 문제를 **측정하고 해결 가능성을 분석하는 진단 작업**입니다.

**코드 수정, CSS 수정, 신규 기능 추가, tarball 재생성, Publish는 하지 마세요.**

## 1. 문제 상황

무인민원발급기에서 최신 SDK v0.5.28을 설치해 검증한 결과, 다음 문제가 발생했습니다.

테스트 환경:
- 화면: 360×667
- 글씨: 매우 크게
- 버튼: 크게
- 고대비
- 쉬운 말 활성화
- 스마트 길잡이 활성화
- 하단 조작 80%
- 느린 안내 비활성화

실제 단계:
`certificate.payment-method`

실제 스마트 길잡이 문구:

"증명서 종류, 발급 부수, 표시 항목과 수수료를 확인해 주세요. 내용이 맞으면 결제 방법을 눌러 가상 결제를 진행하세요."

실제 측정값:
- 안내 패널 최대 높이: 99.56px
- 제목·조작부 높이: 51.19px
- 본문 가용 높이: 44.38px
- 전체 본문 높이: 102.38px
- SDK 판단: 4페이지 필요
- 결과: 최대 2페이지 제한으로 스마트 길잡이 미표시

반면 320×844에서는 같은 안내가 2페이지로 나뉘어 정상 표시됐습니다.

## 2. 진단 목표

**360×667 화면에서 하단 80%와 큰 글씨를 유지하면서, 위 실제 안내 문구를 2페이지 이내에 온전히 보여줄 수 있는지 확인하세요.**

특히 현재 안내창의 제목, 조작부, 내부 여백이 실제로 얼마나 많은 공간을 차지하는지 분석하세요.

단순히 글자 수가 많다고 결론 내리지 말고, SDK의 실제 렌더링 구조와 DOM 측정값을 근거로 판단하세요.

## 3. 공간 구성 상세 측정

가능하면 실제 SDK를 사용하는 독립 테스트 fixture를 만들어 측정하되, SDK 소스나 기존 호스트를 변경하지 마세요.

측정 항목:

1. 안내 패널 전체 최대 높이
2. 안내 패널 실제 높이
3. 제목 높이
4. 닫기·접기 등 조작부 높이
5. 헤더 전체 높이
6. 패널 상하 padding
7. 제목과 본문 사이 간격
8. 본문 실제 사용 가능 높이
9. 본문 font-size
10. 본문 line-height
11. 실제 안내 문구의 줄 수와 전체 높이
12. 한 페이지에 수용 가능한 글자·줄 수
13. 두 페이지에 수용 가능한 실제 내용
14. 페이지 분할 계산 과정
15. 숨겨진 요소나 불필요한 공간이 있는지

측정값을 표로 정리하세요.

## 4. 해결 가능성 비교

다음 세 가지 경우를 코드 변경 없이 비교해 주세요.

### A. 현재 구조 유지

- 현재 안내창 구조
- 기존 제목과 조작부
- 기존 여백
- 하단 80%
- 매우 큰 글씨

필요 페이지 수와 가용 높이를 보고하세요.

### B. 제목·여백 공간 최적화 가능성

실제 측정값을 바탕으로 다음 사항을 분석하세요.

- 불필요한 상하 여백이 있는지
- 제목과 조작부를 같은 행에 배치할 여지가 있는지
- 의미 없는 빈 공간이 있는지
- 헤더 공간을 줄이면 본문 높이가 얼마나 증가하는지
- 본문을 2페이지에 온전히 담기 위한 최소 가용 높이가 얼마인지

**이번 작업에서 실제 CSS나 레이아웃을 변경하지 마세요.**

예상값과 실제 측정값을 구분하세요.

### C. 문구를 간결하게 해야 하는 경우

현재 레이아웃을 합리적으로 최적화해도 2페이지 표시가 어렵다면 그 이유를 설명하세요.

이 경우 안내 문구를 최대 몇 글자·몇 줄 정도로 구성해야 하는지 추정하세요.

단, 자동 요약 기능을 추가하거나 실제 안내 문구를 변경하지 마세요.

문장 축약 예시가 필요하다면 보고서에만 제안하고, 프로젝트에는 적용하지 마세요.

## 5. 다른 화면에서도 비교

다음 화면 크기에서 동일한 안내 문구를 측정하세요.

- 320×844
- 360×667
- 390×844
- 1080×1920

특히 360×667과 320×844 사이에서 가용 높이가 얼마나 달라지는지 비교하세요.

화면 폭뿐 아니라 세로 높이에 따라 결과가 달라지는 원인을 설명하세요.

## 6. 기존 정책 준수

다음 원칙을 바꾸는 제안은 별도 대안으로만 보고하세요.

- 하단 80% 업무 영역 유지
- 매우 큰 글씨 유지
- 스마트 길잡이 최대 2페이지
- 일반 1페이지 10초
- 일반 2페이지 15초
- 느린 안내 20초
- 본문 원문 보존
- 내부 스크롤 없음
- 안내창 상단 8px 고정
- 기존 쉬운 말 접힘·페이지 복원

3페이지 이상을 허용하거나 글씨를 줄이거나 하단 업무 영역을 축소하는 변경은 사용자가 승인하지 않았습니다.

## 8. 최종 보고 형식

다음 질문에 순서대로 답하세요.

1. 360×667에서 정확히 어떤 요소들이 안내 공간을 차지하고 있나요?
2. 실제 본문 가용 높이는 얼마인가요?
3. 현재 안내 문구를 2페이지에 담으려면 페이지당 최소 몇 px가 필요한가요?
4. 제목·조작부·여백을 합리적으로 조정하면 공간을 얼마나 확보할 수 있나요?
5. 공간 조정만으로 해결 가능한가요?
6. 가능하다면 가장 작은 수정 방법은 무엇인가요?
7. 불가능하다면 문구를 어느 정도 간결하게 해야 하나요?
8. 320×844, 360×667, 390×844, 1080×1920 결과는 어떻게 다른가요?
9. 다른 기능에 영향을 줄 위험은 무엇인가요?
10. 코드·tarball·Publish가 변경되지 않았나요?

최종 결론은 반드시 다음 중 하나로 제시하세요.

A. SDK의 여백·헤더 조정만으로 해결 가능

B. SDK 공간 최적화와 호스트 안내 문구 간결화가 함께 필요

C. 현재 조건에서는 문구 간결화가 우선
