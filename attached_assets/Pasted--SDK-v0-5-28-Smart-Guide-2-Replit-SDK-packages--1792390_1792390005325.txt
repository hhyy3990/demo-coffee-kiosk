# 공통 SDK v0.5.28 — Smart Guide 2페이지 회귀 원인 비교 진단

현재 프로젝트는 **데모커피 Replit**입니다.

공통 SDK 경로:
`packages/kiosk-accessibility-sdk/`

이번 작업은 **Smart Guide가 기존에는 2페이지로 정상 표시됐으나 현재 소비자 fixture에서는 4페이지가 필요하다고 판정되어 표시되지 않는 원인을 확인하는 진단 작업**입니다.

현재 수정된 SDK 소스와 기존 tarball은 그대로 유지하세요.

새 기능 추가, SDK 소스 수정, CSS 변경, 표시 정책 변경, tarball 재생성 및 Publish는 하지 마세요.

## 1. 문제 상황

이전에 실제 무인민원발급기에서 다음 조건으로 검증했습니다.

- 화면 크기: 360×667
- stepId: `certificate.payment-method`
- 글씨 매우 크게
- 버튼 크게
- 고대비
- 쉬운 말 활성화
- Smart Guide 활성화
- viewportMode:null → 자동 하단 80%
- slowGuidance:false

실제 안내 원문:

증명서 종류, 발급 부수, 표시 항목과 수수료를 확인해 주세요. 내용이 맞으면 결제 방법을 눌러 가상 결제를 진행하세요.

당시 정상 검증 결과:

- Smart Guide 2페이지
- 패널 높이 98px
- 헤더 높이 44px
- 본문 영역 높이 52px
- 상단 Y=8px
- 조작 버튼 44×44px
- 페이지 전환 약 7.58초
- 총 표시 약 15초
- 본문 잘림 없이 원문 보존

그러나 현재 데모커피 소비자 fixture에서는 동일한 67자 안내에 대해 `fitSmartGuidePages()`가 4페이지가 필요하다고 판단했습니다.

SDK의 최대 2페이지 정책 때문에 안내가 표시되지 않았습니다.

등장 전 10초 타이머는 정상 실행됐습니다.

**이번 진단의 목표는 왜 2페이지였던 안내가 현재 4페이지로 계산되는지 확인하는 것입니다.**

## 3. 브라우저 DOM 실제 측정

현재 360×667 consumer fixture에서 다음 값을 측정하세요.

- viewport 실제 크기
- 자동 하단 80% 적용 여부
- 안내 패널 최대 높이
- 패널 실제 높이
- 헤더 실제 높이
- 제목·카운트다운·버튼 배치
- 상하 padding 및 gap
- 본문 clientHeight와 scrollHeight
- 본문 font-size와 line-height
- 한 페이지에 수용 가능한 줄 수
- `fitSmartGuidePages()`가 사용한 가용 높이
- 실제 문구의 전체 렌더 높이
- SDK가 계산한 필요 페이지 수

Smart Guide가 표시되지 않아 실제 패널을 측정할 수 없다면, 기존 UI를 임의로 변경하지 말고 개발자 도구 또는 테스트용 독립 측정으로 페이지 계산에 사용된 요소의 크기를 확인하세요.

**추정값과 실제 측정값을 구분해서 보고하세요.**

## 4. 실제 무인민원발급기와 fixture 차이 확인

현재 consumer fixture가 실제 무인민원발급기의 레이아웃을 얼마나 정확히 재현하는지 확인하세요.

실제 무인민원발급기 구조:

- `main.stage`가 scrollArea로 등록됨
- 하단 `.device-footer`가 bottomControls로 등록됨
- 하단 80%에서 `.stage`가 실제 스크롤 owner
- footer는 모바일에서 fixed
- 실제 결제 단계 ID는 `certificate.payment-method`
- 실제 안내 원문은 위의 67자 문구

비교할 사항:

1. fixture가 실제로 동일한 360×667 크기를 사용하는지
2. 실제 업무 영역과 footer 높이 차이
3. panel max-height 계산 차이
4. CSS가 다른 버전으로 로드됐는지
5. 제목·카운트다운·버튼 배치 차이
6. Smart Guide가 표시될 때 Easy Language 상태가 달라지는지
7. 테스트용 DOM에서 공간을 추가로 차지하는 요소가 있는지

특히 **기존 성공 환경에서 헤더 44px·본문 52px이었던 구조가 현재도 유지되는지** 확인하세요.

## 5. 구버전과 현재 소스 비교 테스트

가능하다면 동일한 독립 consumer fixture에서 다음 두 빌드를 각각 검증하세요.

A. 기존 89,225바이트 tarball의 SDK

B. 현재 수정된 SDK 소스의 최신 빌드

반드시 같은 화면 크기, 같은 안내 원문, 같은 프로필과 같은 DOM 구조를 사용하세요.

각각 다음을 기록하세요.

- 실제 사용한 SDK JS/CSS 파일 해시
- Smart Guide 필요 페이지 수
- 헤더 높이
- 본문 가용 높이
- 표시 여부
- 원문 보존 여부
- 잘림 여부

기존 버전도 4페이지로 계산된다면 fixture 구조 문제일 가능성을 우선 검토하세요.

기존 버전은 2페이지인데 현재 버전만 4페이지라면 SDK 코드나 스타일 회귀 가능성을 조사하세요.

단, **차이가 확인됐더라도 이번 작업에서 SDK 코드를 수정하지 마세요.**

## 6. fixture 문제인 경우

문제가 fixture의 설정, 단계 연결, DOM 구조 또는 CSS 로딩에서 발생한 것으로 확인되면 **테스트 fixture와 검증 스크립트만 최소 수정**할 수 있습니다.

실제 SDK의 타이머나 Smart Guide 정책은 변경하지 마세요.

fixture 수정 후 다음을 확인하세요.

- 67자 안내가 최대 2페이지로 표시
- 원문 보존 및 잘림 없음
- 기본 2페이지 15초, 약 7.5초 후 전환
- 느린 2페이지 20초, 약 10초 후 전환
- 기본 1페이지 10초
- 종료 후 Easy Language 페이지·접힘 상태 복원
- 패널 상단 Y=8px 유지

동일 fixture에서 기존 SDK와 현재 SDK의 결과를 다시 비교하세요.

## 7. SDK 자체 회귀인 경우

현재 SDK 소스나 CSS에서 실제 회귀가 확인된다면 다음을 보고하고 중단하세요.

- 회귀가 발생한 함수 또는 CSS 규칙
- 기존 버전과 현재 버전의 차이
- 본문 가용 높이가 감소한 이유
- 필요한 최소 수정 범위
- 기존 70% 쉬운 말 개선에 미칠 영향
- 스크롤 안내 위치 계산에 미칠 영향

이번 진단에서는 SDK를 수정하지 마세요.

SDK 오류를 감추기 위해 최대 페이지 수를 3~4페이지로 늘리거나 안내 문구를 축약하지 마세요.
