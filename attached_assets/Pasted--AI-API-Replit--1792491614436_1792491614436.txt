# 데모커피 — 중앙 AI 화면 계획 API 중계 구현 및 무과금 통신 검증

현재 프로젝트는 **데모커피 Replit**입니다.

이번 작업의 목표는 데모커피 키오스크에서 중앙 ‘내 방식 QR’ 서버의 AI 화면 계획 API를 사용할 수 있도록 **안전한 서버 중계 구조를 구현하는 것**입니다.

단, 이번 단계는 실제 OpenAI API 호출 없이 진행합니다.

## 1. 현재 개발 상태

### 데모커피

- SDK 안정 버전: `@naebangsik/kiosk-accessibility-sdk@0.5.31`
- 메뉴 화면 계약: `schemaVersion: 2`
- 화면 ID: `cafe.menu`
- 구조 버전: `menu.v2`
- 구조 해시: `837f86b3`
- React 메뉴 화면에 AI 레이아웃 계획 적용 기능 구현
- `setGroupColumns`, `setGroupFlow`, `setChildBasis` 지원
- Mock 변환 및 주문 회귀 검증 통과

관련 파일:

- `src/accessibility/menuLayoutPlan.ts`
- `src/App.tsx`
- `src/index.css`
- `src/menuLayoutPlan.test.mjs`
- `server.mjs`

### 중앙 ‘내 방식 QR’ 서버

- `POST /api/ai-layout/plan` 구현
- 데모커피 `menu.v2` 정책 등록
- FNV-1a 구조·제약 해시 검증
- v2 연산 조합 검증
- V1~V6 Mock 테스트 통과
- 기존 SHA-256 기반 일반 계약 유지
- 서버 간 Bearer 인증 요구
- `AI_LAYOUT_SERVICE_TOKEN` 미설정
- 실제 서버 간 통신 및 OpenAI 호출 미실행

중앙 서버와 데모커피는 **서로 다른 Replit 프로젝트**입니다.

데모커피에서 중앙 서버 파일을 직접 읽거나 수정할 수 있다고 가정하지 마세요.

## 2. 먼저 실제 중앙 API 계약 확인

데모커피의 현재 화면 모델과 중앙 API의 요청·응답 형식이 완전히 일치하는지는 아직 실제 네트워크로 검증하지 않았습니다.

먼저 데모커피에서 확인 가능한 실제 모델 및 서버 코드를 조사하세요.

중앙 API의 정확한 요청 envelope, 응답 필드 및 인증 방식을 확인할 수 없다면 **추측해서 호환 코드를 확정하지 마세요.**

확인할 항목:

- 중앙 API URL
- 요청 본문 형식
- `hostId` 전달 위치
- 모델 본문 전달 방식
- 응답에서 실제 계획을 추출하는 위치
- 오류 응답 형식
- Bearer 인증 방식
- 요청 타임아웃
- 서버 간 연결 가능 여부

중앙 API 소스가 필요하면 사용자에게 어떤 파일 또는 문서가 필요한지 정확히 보고하세요.

**계약을 확인할 수 없는 부분은 구현을 보류하고 질문하세요.**

## 3. 데모커피 서버 중계 API 구현

기존 `server.mjs`에는 QR 프로필 확인용 `POST /api/qr-profile` 경로가 있습니다.

이 기존 기능은 그대로 유지하세요.

중앙 AI 화면 계획 요청을 전달하기 위한 서버 중계 경로를 추가하세요.

권장 경로:

`POST /api/ai-layout/plan`

구조:

데모커피 브라우저 → 데모커피 서버 → 중앙 AI 서버 → 데모커피 서버 → 브라우저

중계 서버는 다음 역할을 수행해야 합니다.

- 허용된 메뉴 화면 요청만 처리
- 요청 크기 제한
- 입력 구조 검증
- 개인정보 및 사용자 입력값 차단
- 고정된 중앙 서버 URL로만 요청
- 서버 측 Bearer 인증
- 응답 크기 제한
- 응답 구조 검증
- 안전한 오류 처리
- 적절한 타임아웃
- 요청·응답 민감정보 로그 금지

중앙 서버 주소를 요청 본문이나 브라우저 파라미터로 받아 임의 URL로 전송하는 방식은 금지합니다.

중앙 서버가 오류·타임아웃·연결 실패를 반환하면 브라우저는 기존 메뉴 화면을 유지해야 합니다.

## 4. 인증 비밀값 보호

중앙 서버 인증에는 다음 서버 측 환경 변수를 사용하도록 준비하세요.

`AI_LAYOUT_SERVICE_TOKEN`

중요:

- 브라우저 JavaScript에 토큰 노출 금지
- `VITE_` 환경 변수로 토큰 전달 금지
- 소스코드에 토큰 하드코딩 금지
- 프런트엔드 응답에 토큰 포함 금지
- 콘솔이나 요청 로그에 토큰 출력 금지

실제 토큰이 설정되지 않았으면 외부 중앙 API 요청을 수행하지 않고 안전하게 실패하도록 하세요.

이번 작업 중 Agent가 임의의 실제 운영 토큰을 생성하거나 Production Secrets를 변경하지 마세요.

## 5. 중앙 서버 주소

중앙 서비스 주소는 다음과 같습니다.

https://naebangsikqr.replit.app

다만 이는 중앙 서비스의 알려진 주소일 뿐, 현재 개발용 AI API가 해당 Production 주소에 배포되어 있다고 보장하지 않습니다.

**중앙 서버의 Development API가 실제로 접근 가능한 주소인지 먼저 구분하세요.**

중앙 v2 정책은 아직 Production Publish되지 않았으므로 Production 주소에 요청해서 v2 API가 존재한다고 가정하면 안 됩니다.

개발용 서버 주소는 서버 측 설정값으로 분리하세요.

개발 서버가 외부 프로젝트에서 접근할 수 없다면 우회해서 Production을 배포하지 말고 연결 방법을 보고하세요.

## 6. OpenAI 무과금 Mock 검증

이번 단계에서는 실제 OpenAI 호출을 금지합니다.

우선 다음 방식으로 테스트하세요.

### A. 데모커피 서버 내부 Mock

- 중앙 API와 동일한 형식의 정상 응답
- 잘못된 계획
- 인증 실패
- 중앙 서버 오류
- 타임아웃
- 중복 요청
- 오래된 응답

Mock을 통해 중계 API가 안전하게 동작하는지 확인하세요.

### B. 실제 중앙 서버 간 통신 검증

중앙 서버가 **실제 OpenAI 호출 없이 응답하는 기존의 안전한 진단 또는 Mock 경로를 제공하는 경우에만** 서버 간 통신을 확인하세요.

그런 경로가 없다면 실제 중앙 `/api/ai-layout/plan`을 호출하지 마세요.

**서버 간 실제 통신을 아직 확인하지 못한 경우에는 Mock 중계 검증만 완료했다고 정확히 보고하세요.**

검증을 위해 중앙 서버에 임의로 새로운 공개 Mock 경로를 만들거나 인증을 우회하지 마세요.

## 7. React 연동

현재 `src/App.tsx`에는 개발 전용 Mock 계획 주입과 React 레이아웃 적용 기능이 구현되어 있습니다.

실제 AI 서버 연결을 준비할 때는 다음을 지켜주세요.

- 기존 화면을 먼저 정상 표시
- 외부 요청 실패 시 기본 화면 유지
- 유효한 AI 계획만 `validateMenuLayoutPlan()` 통과 후 적용
- 화면 이탈 시 이전 계획 폐기
- QR 설정 변경 시 이전 계획 폐기
- 뷰포트 변경 시 이전 계획 폐기
- 세션 초기화 시 이전 계획 폐기
- 동일 화면 및 제약의 불필요한 중복 요청 방지
- 응답 지연 중에도 메뉴 선택·주문 가능

**이번 작업에서는 실제 중앙 AI 요청을 일반 사용자 흐름에 자동 연결하지 마세요.**

서버 요청을 사용할 수 있는 개발·테스트 전용 함수 또는 비활성화된 연결 경로까지만 준비하세요.

기존 `?mockAiLayout=menu-row` 동작도 유지하세요.

일반 사용자에게 AI 테스트 버튼이나 새로운 설정을 추가하지 마세요.

## 8. 요청·응답 검증

중앙 서버에서 계획이 정상이라고 판정했더라도 데모커피에서 다시 검증해야 합니다.

데모커피의 기존 `validateMenuLayoutPlan()` 검증 규칙을 유지하세요.

특히 다음을 확인하세요.

- `schemaVersion: 2`
- `screenId: cafe.menu`
- `structureHash` 일치
- `constraintHash` 일치
- `viewportClass` 일치
- `setGroupColumns` 허용 열 수
- `setGroupFlow`와 `setChildBasis` 동시 포함
- 유효 열 수 1열 조건
- 연산 순서·중복
- 대상 ID 및 값 범위
- 추가 필드 거부

응답을 안전하게 검증할 수 없으면 적용하지 마세요.
