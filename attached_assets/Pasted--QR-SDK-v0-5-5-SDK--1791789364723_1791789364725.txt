# 내 방식 QR — SDK v0.5.5 스크롤 되돌아감 원인 집중 진단 및 조건부 수정

현재 데모커피 프로젝트에서 공통 접근성 SDK를 개발하고 있습니다.

현재 정식 패키지 버전은 v0.5.4입니다.

SDK 소스에는 넓은 화면에서 발생하던 상단 제목 잘림을 해결하기 위한 안전 중앙 정렬 수정이 반영되어 있습니다. 다만 아직 v0.5.5 tarball은 제작하지 않았습니다.

독립 fixture에서 상단 제목 잘림은 해결됐지만, 마지막 버튼 접근성 검증 중 스크롤이 최하단에 도달한 직후 다시 위로 움직이는 현상이 발견됐습니다.

이번 작업에서는 이 현상의 정확한 원인을 집중 분석하고, 원인이 확인된 경우에만 필요한 수정을 진행해 주세요.

**중요: 이번에는 처음부터 103개 전체 테스트를 다시 실행하지 마세요. 대표적인 실패 사례 1개에서 원인을 먼저 확정하는 것이 목표입니다.**

## 1. 집중 재현 사례

우선 다음 한 가지 조건을 사용합니다.

- 화면: 320×844
- 프로필: 큰 글씨 및 큰 버튼
- viewportMode: 아래쪽 80%
- fixture: min-height 콘텐츠 구조
- 실제 스크롤 소유자: section#stage
- document.scrollTop: 0

이전 측정 결과:

- scrollHeight: 917px
- clientHeight: 675px
- 최대 scrollTop: 242px
- 최대 위치 강제 설정 직후: 242px
- 100ms 이후: 73px
- 마지막 버튼이 다시 화면 밖으로 이동

핵심 질문은 다음과 같습니다.

**왜 scrollTop이 242px에서 73px으로 되돌아가는가?**

## 2. 시간별 스크롤 상태 기록

대표 fixture에서 다음 값을 시간별로 기록해 주세요.

- scrollTop
- scrollHeight
- clientHeight
- 계산된 최대 scrollTop
- 스크롤 요소의 boundingClientRect
- 콘텐츠 첫 제목과 마지막 버튼의 좌표
- 실제 활성 스크롤 소유자
- SDK viewport 위치·높이
- 현재 pointer/touch/wheel 입력 상태

측정 시점:

- 강제 최대 스크롤 직전
- 설정 직후
- 다음 animation frame
- 16ms
- 50ms
- 100ms
- 250ms
- 500ms
- 1초
- 3초

단, 매 측정마다 DOM을 변경하거나 스크롤 위치를 다시 강제로 수정해서는 안 됩니다.

시간 흐름에 따라 자연스럽게 변하는 값을 기록해 주세요.

## 3. 사용자 입력이 완전히 종료된 상태에서 실험

기존 테스트에서는 CDP 터치 스와이프나 휠 입력 이후 관성·부드러운 스크롤이 남아 있었을 가능성이 있습니다.

따라서 아래 두 실험을 분리합니다.

### 실험 A — 사용자 입력 없는 상태

1. 페이지를 새로 로드합니다.
2. SDK viewport 적용과 초기 레이아웃이 안정될 때까지 기다립니다.
3. 휠·터치 입력을 전혀 발생시키지 않습니다.
4. 실제 스크롤 소유자의 scrollTop을 최대값으로 설정합니다.
5. 3초간 위치가 유지되는지 확인합니다.

### 실험 B — 실제 입력 이후

1. 페이지를 새로 로드합니다.
2. 실제 Chromium 휠 또는 CDP 터치 스와이프로 스크롤합니다.
3. 입력 종료 여부를 확인합니다.
4. scroll 이벤트와 위치 변화가 안정될 때까지 기다립니다.
5. 그다음 scrollTop을 최대값으로 설정합니다.
6. 3초간 위치가 유지되는지 확인합니다.

두 결과를 비교해 주세요.

**실험 A는 안정적이고 실험 B만 되돌아간다면 브라우저의 입력·관성 스크롤 문제를 우선 조사합니다.**

## 4. 스크롤 위치를 바꾸는 원인 추적

다음 원인 후보를 분리 실험으로 조사합니다.

A. 브라우저의 smooth scrolling

B. 터치 관성 스크롤 또는 입력 종료 후 남은 애니메이션

C. CSS scroll-behavior

D. CSS scroll-snap

E. 브라우저 scroll anchoring

F. SDK의 ResizeObserver

G. SDK의 MutationObserver

H. SDK의 bottom viewport 레이아웃 재계산

I. SDK의 notifyScreenChange() 지연 초기화

J. 테스트 러너가 추가로 실행한 scrollIntoView 또는 scrollTop 변경

K. 콘텐츠나 스크롤 컨테이너 높이의 비동기 변화

각 원인별로 다음 내용을 보고해 주세요.

- 해당 기능이 실제로 활성화되어 있었는가?
- 스크롤 되돌아감이 발생하는 시점과 관련이 있는가?
- 해당 기능만 진단용으로 비활성화하면 현상이 사라지는가?
- 다른 원인을 통제한 상태에서도 재현되는가?

SDK와 브라우저 동작을 무작정 전부 비활성화한 뒤 성공했다고 판단하지 마세요.

원인을 하나씩 분리해 확인해야 합니다.

## 5. SDK 동작 추적

다음 SDK 기능을 확인합니다.

- bottom-viewport.ts
- scroll-guidance.ts
- layout enhancer
- 화면 전환 notifyScreenChange()
- QR 도크 배치 및 높이 재계산
- ResizeObserver / MutationObserver
- 세션 및 프로필 적용 생명주기

특히 스크롤 위치가 되돌아가는 순간 SDK에서 다음과 같은 동작이 있었는지 확인해 주세요.

- scrollTop 직접 변경
- scrollTo 호출
- scrollIntoView 호출
- 콘텐츠 높이 변경
- viewport 높이 변경
- overflow 변경
- position 또는 transform 변경
- 스크롤 소유자 재설정

진단용 계측은 테스트 코드에 우선 추가하고, SDK의 실제 동작을 바꾸지 않도록 해 주세요.

개발용 계측 코드를 정식 SDK 패키지에 포함시키지 마세요.

## 6. 강제 최대 위치와 실제 사용자 접근성 구분

다음 두 항목을 별도로 검증합니다.

### 레이아웃 자체의 접근성

- 최대 scrollTop으로 이동할 수 있는가?
- 마지막 버튼 전체가 표시되는가?
- 실제 hit-test와 클릭이 가능한가?
- 입력이 없는 안정 상태에서도 위치가 유지되는가?

### 사용자 조작의 접근성

- 휠 입력만으로 마지막 버튼까지 갈 수 있는가?
- 모바일 터치 스와이프로 도달할 수 있는가?
- 스크롤이 중간에서 막히는가?
- 스크롤이 의도치 않게 위로 되돌아가는가?
- 마지막 버튼을 실제 클릭할 수 있는가?

강제 scrollTop만 성공했다고 사용자 접근성을 검증한 것으로 처리하면 안 됩니다.

### 테스트 자동화 문제로 확인된 경우

- 테스트의 입력 좌표·입력 횟수·대기 조건 수정

### 호스트 또는 fixture 계약 문제인 경우

- 잘못된 scrollArea 등록 여부 확인
- 스크롤 소유자와 SDK 어댑터 연결 수정
- 일반적인 SDK 연동 계약 문서화
- 다른 키오스크에도 적용 가능한 수정만 허용

### 원인을 확정하지 못한 경우

- 추가 SDK 변경 금지
- v0.5.5 패키징 금지
- 가장 가능성 높은 원인과 근거·미확인 사항 보고
- 다음 진단에 필요한 최소 실험 제안

## 8. 대표 사례 수정 후 확대 검증

대표 사례에서 원인을 규명하고 정상 동작을 확인한 다음에만 나머지 기존 실패 사례 17개를 검증합니다.

18개 실패 사례가 모두 정상화되면 기존 103개 전체 fixture를 재실행합니다.

검증 항목:

- 상단 제목 잘림 없음
- 마지막 버튼까지 실제 스크롤
- 스크롤 위치 안정성
- 마지막 버튼 전체 표시
- 버튼 hit-test 및 클릭
- 이중 스크롤 없음
- 가로 넘침 없음
- QR 도크·고정 조작부 충돌 없음
- 하단 60·70·80% 유지

103개 검사에서 필수 실패가 남으면 통과로 보고하지 마세요.
