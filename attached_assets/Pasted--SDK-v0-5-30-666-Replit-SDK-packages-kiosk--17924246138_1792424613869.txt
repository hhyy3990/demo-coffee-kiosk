# SDK v0.5.30 — 666자 긴 안내의 원문 보존 및 테스트 실패 확인

현재 프로젝트는 **데모커피 Replit**입니다.

공통 SDK:
`packages/kiosk-accessibility-sdk/`

이번 작업은 consumer 브라우저 검증에서 발견된 **666자 원문·21페이지·수집 문구 73자** 현상의 원인을 확인하는 것입니다.

**진단을 우선하며, SDK 기능 코드·CSS·버전·tarball은 변경하지 마세요.**

## 1. 판단 기준

320×844 화면에서 666자 안내가 21페이지로 나뉘는 것 자체는 정상일 수 있습니다.

페이지당 평균 약 32자이므로, 매우 큰 글씨와 제한된 안내 영역을 고려하면 합리적인 결과일 수 있습니다.

**21페이지라는 이유만으로 SDK 오류라고 판단하거나 페이지 수를 줄이려고 하지 마세요.**

확인해야 하는 것은 다음 두 가지입니다.

1. 실제 21페이지에 원문 666자가 빠짐없이 보존되어 있는가?
2. 테스트가 페이지를 전부 읽지 못해 73자만 수집한 것인가?

## 2. 실패한 테스트 조사

`packages/kiosk-accessibility-sdk/scripts/test-consumer-qr-entry-browser.mjs`

해당 스크립트의 긴 Easy Language 안내 검사를 확인하세요.

- 666자 원문이 만들어지는 위치
- 실제 원문 길이
- 총 페이지 수 계산 방식
- 페이지 이동 방법
- 페이지별 텍스트 수집 방식
- 페이지 전환 후 렌더링 대기 방식
- 73자만 수집된 이유

실제 테스트 문자열과 수집된 문자열을 비교하되, 콘솔에는 불필요하게 원문 전체를 반복 출력하지 마세요.

## 3. 브라우저에서 직접 확인

기존 consumer fixture를 재사용하세요.

조건:

- 320×844
- 기존 테스트와 동일한 글씨·버튼·화면 위치 설정
- 동일한 666자 원문
- Easy Language 활성화

다음을 측정하세요.

1. 전체 페이지 수
2. 각 페이지에서 실제 표시되는 글자 수
3. 이전·다음 버튼 동작
4. 마지막 페이지 도달 여부
5. 페이지 이동 중 전체 페이지 수 안정성
6. 모든 페이지의 텍스트를 순서대로 이어 붙였을 때 원문과 정확히 일치하는지
7. 중복·누락·순서 변경 여부
8. 글자 잘림이나 버튼 겹침 여부

공백·줄바꿈 정규화가 필요한 경우에는 원문 비교와 별도로 결과를 보고하세요. 실제 문자 누락을 정규화로 감추지 마세요.

## 4. 테스트 오류인 경우

다음과 같은 원인이 확인되면 **관련 테스트 코드만 최소 수정**할 수 있습니다.

- 일부 페이지만 읽고 검사 종료
- 페이지 전환 완료 전에 텍스트 수집
- 잘못된 페이지 선택자
- 버튼 상태를 잘못 판정
- 총 페이지 수가 아니라 고정된 횟수만 반복
- 이전에 제거한 접기 버튼을 기준으로 검사

수정 후에는 마지막 페이지까지 실제로 이동하고, 원문 전체 보존을 검증해야 합니다.

단순히 기대값을 73자로 바꾸거나 페이지 수 검사를 제거해 통과시키지 마세요.

## 5. 실제 SDK 문제인 경우

원문이 실제로 누락되거나 특정 페이지를 표시할 수 없다면 다음을 보고하세요.

- 최초로 누락되는 페이지
- 누락된 텍스트 범위
- 관련 SDK 함수
- 재현 조건
- 최소 수정 후보

**SDK 코드는 수정하지 말고 사용자 승인을 기다리세요.**

페이지 수를 억지로 줄이거나 본문 글씨를 축소하지 마세요.
