# 내 방식 QR — 공통 SDK v0.5.4의 넓은 화면 상단 잘림 원인 분석 및 조건부 v0.5.5 개발

현재 데모커피 프로젝트에서 공통 접근성 SDK `@naebangsik/kiosk-accessibility-sdk@0.5.4`의 소스를 개발·관리하고 있습니다.

v0.5.4에서는 `notifyScreenChange(screenId)` 공개 API를 도입해 업무 화면 전환 시 스크롤 위치를 초기화하는 문제를 해결했습니다.

무인민원발급기에도 v0.5.4를 설치한 결과, 업무 화면 전환과 처음화면 복귀 시 스크롤 초기화는 정상 작동했습니다.

그러나 넓은 데스크톱 화면에서 **하단 조작 모드를 적용하면 첫 화면의 상단 제목이 실제 표시 영역 밖으로 밀려 잘리는 문제**가 추가로 확인됐습니다.

이번 작업의 목적은 이 문제를 독립적인 SDK 테스트 환경에서 재현하고, 공통 SDK에서 해결해야 하는 문제인지 호스트 레이아웃 계약의 문제인지 판정하는 것입니다.

**SDK 범용성을 최우선으로 하며, 원인이 확인되기 전에는 SDK v0.5.5를 제작하지 마세요.**

---

## 1. 실제 무인민원발급기에서 확인된 문제

1440×900 브라우저 화면에서 v3 QR 모의 프로필을 적용했습니다.

프로필 설정:

- 큰 글씨
- 큰 버튼
- 고대비
- 하단 조작 모드 80%

측정 결과:

- SDK의 `.stage` 표시 영역 시작: y=166px
- 실제 `.stage` 높이: 662px
- 첫 번째 제목 시작: y=144px
- 첫 제목의 하단: y=175px
- 제목 상단이 표시 영역보다 약 22px 위에 있음
- 제목 중앙 hit-test 결과가 제목 H1이 아닌 DIV로 확인됨
- QR 미적용 상태에서는 제목이 정상 표시됨

기존 호스트 레이아웃에는 다음 특성이 있습니다.

- `.screen-shell`의 최소 높이 약 780px
- 세로 중앙 정렬 구조
- SDK 적용 시 표시 영역은 약 662px
- 콘텐츠 높이가 표시 영역보다 클 수 있음

따라서 콘텐츠의 최소 높이 또는 중앙 정렬 방식과 SDK의 제한된 하단 viewport 사이에서 충돌했을 가능성이 있습니다.

현재는 가설이며, 실제 원인을 테스트로 확인해야 합니다.

## 2. 최우선 작업 원칙

이번 작업에서 반드시 지켜야 할 원칙입니다.

1. 무인민원발급기 프로젝트를 직접 수정하지 않습니다.
2. SDK에 무인민원발급기 전용 클래스나 CSS 선택자를 추가하지 않습니다.
3. SDK에 780px, 662px, 1440×900 등 특정 환경의 숫자를 해결 코드로 하드코딩하지 않습니다.
4. 화면을 비율에 맞춰 축소하는 방법 A를 도입하지 않습니다.
5. 기존 글씨·버튼 크기를 줄이지 않습니다.
6. 공통 SDK 문제라면 SDK에서 범용적으로 수정합니다.
7. 호스트 계약 문제라면 재사용 가능한 연동 원칙을 문서화합니다.
8. 원인이 불확실하다면 추정만으로 버전을 올리지 않습니다.

**목표는 카페와 무인민원발급기만 고치는 것이 아니라, 처음 연결하는 병원 키오스크에서도 동일한 SDK가 동작하도록 만드는 것입니다.**

## 3. SDK 하단 viewport의 기존 구조 분석

다음 코드를 조사해 주세요.

- `setViewportMode()`
- v3 프로필의 viewportMode 자동 적용
- bottom viewport의 대상 요소 등록 및 높이 계산
- `configureTarget()` 및 관련 레이아웃 처리
- QR 도크 높이 측정
- 고정 하단 조작부 측정
- scrollArea 처리
- SDK가 설정하는 position, overflow, height, min-height, max-height
- 화면 전환 API `notifyScreenChange()`
- ResizeObserver 및 MutationObserver
- 기존 스타일 복원 및 endSession()

특히 다음 질문에 답해 주세요.

**SDK가 표시 영역의 높이를 제한했을 때, 그 안에 있는 콘텐츠의 최소 높이와 세로 정렬까지 안전하게 처리할 수 있는가?**

콘텐츠가 표시 영역보다 크면 위로 잘리는 대신 스크롤로 접근할 수 있어야 합니다.

SDK가 호스트의 내부 레이아웃을 어느 범위까지 조정할 수 있고, 어떤 부분은 호스트가 어댑터를 통해 알려줘야 하는지도 구분해 주세요.

## 4. 독립 재현 fixture 구성

데모커피나 무인민원발급기 화면 코드를 복사하지 말고, 일반적인 HTML·CSS로 독립 fixture를 만듭니다.

### Fixture A — 최소 높이 콘텐츠

- 콘텐츠 컨테이너에 큰 min-height 부여
- 실제 viewport보다 콘텐츠 높이가 큼
- 내부에 상단 제목과 긴 메뉴 목록
- 하단 viewport 60·70·80% 적용

### Fixture B — 세로 중앙 정렬

- 부모가 flex 또는 grid 중앙 정렬
- 자식 콘텐츠 높이가 사용 가능한 영역보다 큼
- 상단 제목과 마지막 버튼을 배치
- SDK 적용 전후 상단 접근성 확인

### Fixture C — 최소 높이 + 중앙 정렬

- min-height 약 780px인 콘텐츠
- 세로 중앙 정렬
- 1440×900 화면
- 하단 80% 적용
- 표시 영역은 실제 SDK 계산값 사용
- 첫 제목이 위쪽으로 밀리는지 확인

### Fixture D — QR 도크와 고정 조작부

- QR 도크
- 기존 고정 하단 버튼
- 하단 60·70·80%
- 큰 글씨·큰 버튼
- 제한된 공간에서 상단·하단 콘텐츠 접근 확인

### Fixture E — 일반 스크롤 구조

- 문서 스크롤형 키오스크
- 내부 스크롤형 키오스크
- 화면 전환에 따라 스크롤 소유자가 달라지는 구조

모든 fixture는 SDK 공개 API와 일반적인 레이아웃 어댑터를 이용해야 합니다.

## 5. 상단 잘림 여부 판정

스크롤 위치가 0이라는 이유만으로 정상이라고 판단하지 마세요.

각 fixture에서 다음을 측정합니다.

- SDK viewport의 top / bottom / height
- 실제 스크롤 영역의 top / bottom / height
- 콘텐츠 컨테이너의 min-height
- 상단 제목의 boundingClientRect
- 상단 제목의 실제 hit-test 결과
- document.scrollTop
- 내부 scrollArea.scrollTop
- 최대 스크롤 거리
- overflow 및 align-items 속성
- 마지막 버튼의 표시·클릭 가능 여부

다음 조건이 필수입니다.

**스크롤을 맨 위로 이동했을 때 첫 제목 전체가 실제 콘텐츠 표시 영역 안에 보여야 합니다.**

또한 스크롤을 끝까지 이동하면 마지막 콘텐츠에 접근할 수 있어야 합니다.

스크롤바만 숨기거나 콘텐츠를 위로 잘라낸 상태를 정상 처리하면 안 됩니다.

## 6. SDK 결함과 호스트 계약 문제 구분

다음 기준으로 판정합니다.

### A. 공통 SDK 결함

독립 fixture에서도 SDK가 제한한 viewport 때문에 상단 콘텐츠가 잘리고, SDK 공개 API나 정상적인 어댑터 등록만으로 해결할 수 없는 경우입니다.

이 경우:

- SDK 공통 원인 분석
- 범용 레이아웃 수정
- 독립 fixture 재검증
- 데모커피 회귀
- 필요 시 SDK v0.5.5 제작

### B. 호스트 레이아웃 계약 문제

호스트의 최소 높이·중앙 정렬·스크롤 컨테이너 등록 때문에 문제가 발생하지만, 공통 SDK에서 제공하는 기존 어댑터 계약을 올바르게 사용하면 해결되는 경우입니다.

이 경우:

- SDK 버전 변경 없이 원인 보고
- 필요한 호스트 어댑터 등록 또는 레이아웃 계약 설명
- 카페와 병원 등 다른 키오스크에 적용 가능한 일반적인 가이드 작성
- 무인민원발급기 전용 해결 코드는 작성하지 않음

단, 정상적인 어댑터 연결만으로 해결할 수 없는 일반적인 레이아웃 유형이라면 SDK의 기능 부족 가능성을 우선 검토해 주세요.

### C. 복합 원인

호스트의 레이아웃 특성이 문제를 유발하지만 SDK에서도 이를 범용적으로 감지하거나 안전하게 처리해야 하는 경우입니다.

이 경우 양쪽 책임을 구분하고, 가능한 한 SDK 공통 기능으로 보완해 주세요.

**특정 호스트의 CSS를 강제로 덮어쓰는 방식은 마지막 수단으로도 사용하지 마세요.**

## 7. 수정이 필요하다면 지켜야 할 원칙

공통 SDK 결함이 확인된 경우에만 수정합니다.

목표 동작:

- 하단 viewport 높이 제한 유지
- 콘텐츠 자체 축소 없음
- 글씨와 버튼 크기 유지
- 상단 콘텐츠 잘림 없음
- 하단 콘텐츠 접근 가능
- 하나의 명확한 스크롤 영역 사용
- QR 도크·기존 고정 조작부와 충돌 없음
- 화면 전환 시 첫 콘텐츠부터 표시
- 모달 열기·닫기 시 기존 위치 유지

특히 부모 flex/grid의 중앙 정렬 때문에 자식이 위로 넘치는 상황을 어떻게 해결할지 검토해 주세요.

필요한 경우 SDK가 레이아웃 어댑터를 통해 **실제 콘텐츠 정렬 컨테이너 또는 스크롤 대상**을 명시적으로 전달받는 일반적인 기능을 설계할 수 있습니다.

하지만 기존 API로 충분한 경우 불필요한 새 공개 API를 만들지 마세요.

SDK가 모든 호스트 DOM 자손을 무차별적으로 수정하는 방식도 금지합니다.

## 8. 화면 전환 API 회귀

v0.5.4에서 구현한 `notifyScreenChange()`는 반드시 유지합니다.

다음 상황을 검증해 주세요.

- 새 화면에서 scrollTop=0
- 첫 제목 전체 표시
- QR 도크 생성·제거 후 제목 표시
- 하단 viewport 60·70·80% 전환
- document ↔ 내부 scrollArea 전환
- 같은 화면 ID 반복 통지 시 기존 위치 유지
- 모달 열기·닫기 시 기존 위치 유지
- 사용자가 스크롤을 시작한 뒤 늦은 초기화 없음
- 세션 종료 후 첫 화면 복원

상단 잘림을 고치면서 화면 전환의 스크롤 초기화가 다시 고장 나면 안 됩니다.

## 10. QR 프로필과 기존 기능 회귀

다음 기능을 유지합니다.

- QR v1/v2/v3
- viewportMode null 및 60·70·80%
- `applyProfile()`을 통한 자동 적용
- QR 도크 첫 화면 전용 표시
- 기존 고정 하단 조작부와 공존
- 스크롤 안내 `no-safe-space` 수정
- 스마트 길잡이와 음성 안내
- 화면 전환 `notifyScreenChange()`
- 세션 종료 `endSession()`
- QR 모달 열기·닫기
- 프로필 교체와 반복 적용
- 데모커피 주문 전체 흐름

기존 터치 영역과 마지막 메뉴 경계 문제는 이번 작업에서 별도로 수정하지 않습니다. 단, 이번 수정으로 해당 문제가 악화되면 회귀 실패로 기록해 주세요.

## 11. SDK v0.5.5 제작 조건

**공통 SDK 수정이 실제로 필요하고, 독립 재현·수정·회귀 검증이 모두 성공한 경우에만 v0.5.5를 제작합니다.**

조건을 충족하면 다음 tarball을 생성해 주세요.

`packages/kiosk-accessibility-sdk/releases/naebangsik-kiosk-accessibility-sdk-0.5.5.tgz`

확인 사항:

- 패키지명 `@naebangsik/kiosk-accessibility-sdk`
- 버전 0.5.5
- 수정 JavaScript·CSS 및 타입 선언 포함
- 기존 v0.5.4 이하 tarball 보존
- README에 레이아웃 계약 및 수정 내용 기록

반대로 SDK 수정 없이 호스트의 올바른 어댑터 연결만으로 해결 가능하다면 v0.5.4를 유지하고, 필요한 연동 방법만 보고해 주세요.
