# 내 방식 QR — AI 실시간 키오스크 화면 변환 도입을 위한 구조 조사

현재 프로젝트는 **데모커피 Replit**입니다.

데모커피는 공통 접근성 SDK `@naebangsik/kiosk-accessibility-sdk`의 원본 프로젝트입니다.

현재 공통 SDK 최신 검증 버전은 **v0.5.31**입니다.

이번 작업은 우리가 가장 중요하게 개발하려는 **AI 실시간 키오스크 화면 변환 기능**을 도입하기 위한 사전 기술 조사입니다.

**반드시 읽기 전용으로 조사하세요. 코드 수정, 신규 기능 구현, 패키지 배포, DB 변경, Publish는 승인하지 않습니다.**

## 1. 최종적으로 구현하려는 기능

현재 시스템은 사용자가 만든 QR 프로필에 따라 키오스크 화면의 글씨 크기, 버튼 크기, 고대비, 하단 배치, 쉬운 말 안내, 스마트 길잡이 등을 적용합니다.

그러나 현재는 사전에 작성된 화면 구조와 SDK 규칙에 의존하고 있습니다.

추가하려는 기능은 다음과 같습니다.

1. 사용자가 QR을 적용합니다.
2. SDK가 현재 키오스크 화면의 실제 구조를 파악합니다.
3. 사용자 접근성 설정과 화면 구조 정보를 AI에 전달합니다.
4. AI가 해당 화면에 적합한 접근성 구성안을 실시간으로 생성합니다.
5. SDK가 구성안을 검증하고 화면에 적용합니다.
6. 업무 단계가 바뀌면 새로운 화면에 대해서도 필요한 경우 AI가 다시 구성안을 생성합니다.
7. AI 실패 시 기존 SDK의 규칙 기반 화면으로 안전하게 복귀합니다.

여기서 **실시간 변환**은 매 프레임 AI를 호출한다는 의미가 아닙니다.

새 업무 화면에 처음 진입하거나 구조가 실질적으로 변경됐을 때 AI가 구성안을 생성하고 적용하는 방식을 우선 고려합니다.

기존에 분석한 화면과 동일한 조건이라면 캐시 재사용도 검토할 수 있습니다.

## 2. 조사 목적

다음 질문에 실제 소스 코드와 파일 경로를 근거로 답하세요.

### A. SDK가 현재 화면을 얼마나 파악할 수 있는가?

다음 항목을 확인하세요.

- 현재 화면의 제목과 업무 단계 ID
- 메뉴·버튼·입력창·선택 항목
- 화면 요소의 텍스트
- 각 요소의 역할과 계층 구조
- 요소의 표시·숨김 상태
- 실제 위치와 크기
- 스크롤 영역
- 고정 QR 도크와 footer
- 화면 변경 감지 방식

특히 다음을 구분하세요.

**현재 SDK가 이미 수집하는 정보 / 호스트가 명시적으로 전달하는 정보 / 새로 수집해야 하는 정보**

DOM을 읽는 것만으로 충분한지, 호스트에서 별도의 화면 구조 데이터를 제공해야 하는지도 판단하세요.

### B. 기존 화면 변환 기능 재활용 가능성

SDK v0.5.31에서 다음 기능을 실제로 처리하는 파일과 함수를 조사하세요.

- 글씨 크기
- 버튼·터치 영역 크기
- 고대비
- 하단 60·70·80% 배치
- 쉬운 말 안내
- 스마트 길잡이
- 안내 페이지 분할
- 스크롤 안내
- 고정 조작부 회피
- 프로필 적용 및 세션 초기화

AI가 이 기능들의 값을 결정하거나 조합하는 방식으로 연결할 수 있는지 확인하세요.

가능하면 **기존 렌더링 코드를 다시 만드는 대신, 기존 SDK에 안전한 구성안을 전달하는 방식**을 우선 검토하세요.

### C. AI가 실제로 무엇을 바꿀 수 있어야 하는가?

다음 두 방식의 장단점을 비교하세요.

**방식 1. AI가 기존 SDK 설정을 선택·조합**

예:
- 어떤 화면 배치를 사용할지
- 버튼·글씨 크기 우선순위
- 안내를 어느 순서로 보여줄지
- 콘텐츠가 넘칠 때 어떻게 처리할지

**방식 2. AI가 개별 UI 요소의 접근성 배치를 제안**

예:
- 메뉴를 어떤 순서로 보여줄지
- 설명 영역을 어디에 배치할지
- 한 화면에 표시할 요소를 어떻게 묶을지
- 화면 크기에 따라 페이지를 어떻게 나눌지

다음 조건을 반드시 지키면서 어느 수준까지 구현할 수 있는지 검토하세요.

- 사용자가 직접 정한 QR 설정은 AI가 임의로 무시하거나 변경하지 않음
- 원래 메뉴와 업무 기능 유지
- 원래 버튼의 이벤트·동작 보존
- 필수 입력창·확인 버튼 누락 금지
- 결제·발급 등 업무 단계 임의 변경 금지
- AI가 임의의 HTML·JavaScript를 생성해 실행하는 방식 지양
- 기존 SDK의 접근성 기능과 충돌 금지

이번 조사에서는 **실제로 화면을 AI가 변환했다는 시연을 할 수 있을 정도의 최소 구현 범위**를 제안하세요.

단순히 이미 존재하는 QR 설정값을 AI가 다시 추천하는 것은 이번 목표를 충족하지 못합니다.

### D. AI에 전달할 화면 정보와 개인정보 보호

우리는 향후 다양한 키오스크에 이 기능을 적용하려 합니다.

그러나 현재 무인민원발급기에는 주민등록번호 등 개인정보를 입력하는 화면도 있습니다.

다음 내용을 조사하세요.

- DOM에서 화면 구조만 추출하는 방법
- input의 현재 입력값 제외
- 주민등록번호·이름·전화번호·주소·결제정보 제외
- 민감한 안내 문구나 사용자 입력 텍스트 제외 방법
- 버튼 역할과 구조를 전달하면서 개인정보를 보내지 않는 방법
- AI 요청·응답 로깅 시 개인정보 노출 방지
- 화면 변경 때마다 불필요하게 외부 AI 요청이 발생하지 않도록 하는 방법

**AI에는 입력값이 아니라 화면의 구조, 역할, 안전하게 분류한 정적 UI 정보만 전달하는 설계를 우선하세요.**

화면 정보 수집이 불확실한 영역은 외부 전송에서 제외하는 보수적 접근을 권장합니다.

### E. AI 서버 연결 위치

현재 중앙 ‘내 방식 QR’ 사이트에는 OpenAI Responses API를 이용하는 접근성 설정 추천 기능이 있습니다.

현재 데모커피와 공통 SDK의 서버 구성을 조사한 뒤 아래 대안을 비교하세요.

1. 중앙 ‘내 방식 QR’ 서버에 AI 화면 변환 API 추가
2. 데모커피 서버에 AI 화면 변환 API 추가
3. 별도 AI 화면 변환 서버 구축

비교 기준:

- 공통 SDK를 여러 키오스크에서 사용할 수 있는지
- OpenAI API 키 보안
- 사용자 개인정보 보호
- 서버 유지보수 부담
- 응답 속도와 장애 대응
- Replit 프로젝트 간 연동 난이도
- 개발 기간과 테스트 부담

**SDK에 OpenAI API 키를 포함하는 방식은 금지합니다.**

가능하면 이미 존재하는 중앙 서버를 활용하는 방향을 우선 검토하되, 현재 소스 코드를 확인하지 않은 상태에서 확정하지 마세요.

### F. AI 응답 검증 및 안전한 적용

AI가 반환하는 구성안을 그대로 신뢰하지 않고, SDK가 허용된 값만 적용하도록 설계할 방법을 조사하세요.

최소 검토 항목:

- JSON 등 구조화된 결과
- 허용된 요소 ID만 참조
- 허용된 UI 변경 유형만 적용
- 글씨·버튼 크기 최소값 유지
- 필수 업무 요소 보존
- 고정 QR 도크·footer 가림 방지
- 화면 밖 요소 또는 잘린 버튼 방지
- AI 응답 지연·오류·타임아웃 시 기존 화면 유지
- 프로필 해제·업무 초기화 시 AI 변경 사항 완전 복원
- 이전 화면의 늦게 도착한 AI 결과가 다음 화면에 적용되지 않도록 방지

기존 SDK v0.5.31에서 재활용할 수 있는 검증·정리 기능도 찾아주세요.

## 3. 첫 구현에 사용할 시연 화면 선정

첫 구현은 **데모커피에서 시작**하는 방향을 우선 검토하세요.

다음 업무 단계 중 AI 화면 변환 차이를 명확히 보여줄 수 있는 화면을 찾아주세요.

- 메뉴 목록
- 메뉴 상세 및 옵션 선택
- 장바구니
- 결제 확인

각 화면에서 어떤 구조 정보를 얻을 수 있고, AI가 실제로 어떤 변경을 제안하면 기존 규칙 기반 화면과 차별화되는지 설명하세요.

**첫 구현에서는 하나 또는 두 개의 대표 화면으로 범위를 제한하는 방안도 제안하세요.**

그 후 무인민원발급기에 확대할 때 추가로 필요한 부분을 구분하세요.

## 4. 현재 SDK의 확장 가능성 및 위험 요소

특히 다음 문제를 조사하세요.

- React 렌더링과 SDK의 DOM 변경이 충돌하는지
- MutationObserver와 AI 화면 변환이 서로 반복 호출되는지
- 기존 쉬운 말·스마트 길잡이와 AI 결과가 중복 표시되는지
- 화면 크기 변경 시 구성안을 다시 생성해야 하는지
- 동일 화면 재진입 시 캐시를 사용할 수 있는지
- 세션 종료 후 AI 관련 상태가 남지 않는지
- 키오스크별 DOM 구조 차이를 어떻게 처리할지
- AI 요청이 오래 걸려도 주문·발급 기능을 막지 않는지

특히 SDK에서 직접 DOM을 재배치하는 방식과, 호스트 React 화면에 구조화된 구성안을 전달해 렌더링하는 방식을 비교하세요.

## 5. 반드시 피해야 할 구현

다음 방식은 제안하지 마세요.

- AI가 임의의 HTML·JavaScript를 생성해 실행
- 실제 사용자 입력값을 AI에 전송
- AI가 주문 금액·결제 정보·발급 내용을 수정
- 기존 이벤트 핸들러를 파괴하는 DOM 재생성
- 사용자의 QR 설정을 AI가 임의 변경
- 모든 화면 변경에 무조건 외부 AI 요청
- AI 응답이 올 때까지 키오스크 이용을 중단
- 기존 SDK를 전면 재작성
- 처음부터 모든 업종의 키오스크에 적용할 수 있다고 가정
